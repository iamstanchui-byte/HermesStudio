## 1. Context

`proj-29b2990d` (2026-08-03) exposed a duplicate-dispatch bug where the same
step name (`check-total`) had two live `pending` rows — one created by
`apply-workflow` (short `t-XXX` id), one created by SOUL dispatch (UUID id).
A loopback reset marked both `pending` again, and the supervisor dispatched
both in parallel, causing 2x LLM calls per iteration (8 of 12 calls were
duplicate dispatches; 1.7M tokens vs an expected ~600K, ~3x cost).

## 2. Accepted Fix: 2-Layer Defense

| Layer | Commit | Responsibility |
|---|---|---|
| Primary (clean DB) | `ea26b40` | `dispatch_step()` archives any existing `pending/dispatched/assigned/failed/skipped` task with the same `(project_id, name)` before creating a new row. `running` tasks are explicitly skipped to protect in-flight work. |
| Safety net (no dispatch) | `000cce6` | `_find_ready_tasks` uses a `NOT EXISTS` subquery to keep only the latest-`created_at` pending row per name, even if archive was skipped or raced. |

**Estimated savings:** ~65% reduction (1.7M → ~600K tokens) for similar
duplicate-prone projects going forward.

**Rationale for keeping both layers:** `ea26b40` fixes the root cause (DB stays
clean, dashboard doesn't show ghost rows), `000cce6` is cheap insurance
against any future dispatch path that forgets to archive.

## 3. Hardening Follow-ups (before adding new features)

These are process/robustness gaps in the 2-layer fix itself, not new scope:

1. **Transactional archive+create.** `ea26b40`'s archive-then-create is two
   separate statements. Two concurrent dispatchers for the same
   `(project_id, name)` could both pass the "no live duplicate" check before
   either commits. Wrap archive + insert in one DB transaction (or a
   `SELECT ... FOR UPDATE`-equivalent lock for SQLite: a single writer
   critical section) to remove the race window.
2. **Regression tests for the interaction, not just each layer alone.**
   Add a test that (a) archive fires correctly for each of
   `pending/dispatched/assigned/failed/skipped`, and is a no-op for
   `running`; (b) if archive is *intentionally* skipped (simulating a bug),
   the `000cce6` dedupe still returns exactly one row. Today the two layers
   are tested independently (`test_supervisor_archive_filter.py`); no test
   exercises "archive path disabled, dedupe as sole defense."
3. **Runtime invariant check.** Add a lightweight assertion/alert: for any
   `(project_id, name)`, there should never be more than one `running` row.
   Surface a warning on the dashboard (not just a log line) if violated —
   this is the cheapest early-warning signal for a regression in either
   layer.

## 4. Declined / Deferred Items (for the record)

| Item | Decision | Reason |
|---|---|---|
| Narrow loopback reset scope | Declined (for now) | The savings-demo workflow depends on full-chain reset (`add-savings` re-run grows a file across iterations). Narrowing would break that demo's semantics. |
| Task-level result cache | Deferred | Needs a cache layer + invalidation strategy; separate, larger scope of work. |
| Token usage monitoring dashboard | Deferred | Lower ROI specifically for *token cost reduction* (it's observability, not a fix). Worth doing later for visibility, not urgent. |

### 4.1 Proposed compromise for loopback reset

Rather than a global "narrow reset" change, introduce an explicit
**reset policy** on the workflow package / plan metadata, so behavior is
opt-in per workflow instead of a global tradeoff:

- `full_chain_reset` (current default — required by savings demo)
- `failed_branch_reset` (only the failed task + its dependents)
- `latest_instance_only` (skip re-running steps that already have a valid
  latest result)

This keeps today's demo behavior intact while unblocking future workflows
that don't need full-chain semantics.

## 5. Largest Remaining Waste Source: Hermes 0.19.1 Micro-Compaction

The original draft flagged conversation history growth (8x prompt expansion
across loopback iterations: 36K → 302K tokens) as the largest remaining
waste source, and proposed two approaches:

1. **Sliding window on resume** — cap history to last N turns. Originally
   thought blocked because `hermes` 0.17.0 CLI didn't expose a history-cap
   option.
2. **Pre-dispatch summarization** — extra LLM call to compress prior turns.

**Status update (2026-08-03, commits `fd92b9b` + `c3e998d`):** Production is
on `hermes 0.19.1` (not 0.17.0 as the original draft assumed), which ships a
native `compression` config block for per-turn micro-compaction. We chose
the **hermes-native path** — no server-side truncation, no extra LLM call,
no state.db patching — wrapper writes the compaction config into hermes's
own `~/.hermes/config.yaml` on every tick. This preserves the hermes cache
prefixes that summarization would invalidate, and is implementation-cheap
(no extra round-trip).

**Why not C (patch `state.db` directly to drop old messages)?** Rejected
unconditionally. hermes owns `state.db` schema and integrity; orchestrator
writing to it from outside is a footgun the moment hermes ships a
migration. The native `compression` block achieves the same prompt-size
floor without the integrity risk.

### 5.1 Implementation Summary

**Server side (`fd92b9b`, "Phase A: per-task conversation history window"):**

- `config.py`: `DEFAULT_CONFIG.supervisor.default_max_history_turns: 6`
  (≈ 3–6K tokens of overhead vs the 80–300K actual prompt size we saw in
  the repro; matches the asymptotic floor of the growth curve).
- `api/plans.py`: `ProjectPlan.max_history_turns: int | None = None` with
  Pydantic validator accepting `0..200` (0 = no cap, >200 rejected as
  typo guard). Round-trips through `plan_json`; legacy v3.11-era plans
  default to `None` (fall through to server config).
- `orchestrator/soul_dispatch.py` — `_create_dispatched_task` resolves the
  effective value at dispatch time with 4-tier priority:
  1. `step_dict["max_history_turns"]` (per-step override)
  2. `projects.plan_json.max_history_turns`
  3. `config.supervisor.default_max_history_turns`
  4. hard-coded `6` (defensive fall-back)
  Writes the resolved value into `task.params["_max_history_turns"]`
  (underscore prefix = orchestrator-internal, wrapper skips from
  user-facing rendering).
- `api/agents.py`: new HMAC-gated endpoint
  `GET /api/agents/{id}/max_history_config` returning
  `{agent_id, value, source}`. The wrapper's config-poll cycle fetches
  this on every tick — so editing `config.yaml` takes effect on the
  wrapper's next poll, **no wrapper restart needed** for value changes.

**Wrapper side (`c3e998d`, "Phase B: hermes 0.19.1 micro-compaction opt-in"):**

- `_max_history_turns_cache: int = 6` module-level default.
- `_poll_max_history_config()` — nested helper called from the wrapper's
  existing config-poll cycle; hits the HMAC endpoint, caches the value.
- `_apply_hermes_compaction_config(profile_root, N)` — writes
  `compression.protect_last_n: N` + `threshold: 0.30` into the per-profile
  `~/.hermes/config.yaml`. Atomic write via temp-file + `os.replace()` to
  avoid torn writes if the wrapper is killed mid-write. `threshold: 0.30`
  is below the hermes default of `0.50` because the savings demo with
  30+ iterations routinely exceeds 30% context — trigger earlier.
- `_capture_session_tokens()` — extends to read `sessions.message_count`
  from `~/.hermes/state.db` (SQLite), aliased as `history_turn_count` in
  the returned dict.
- `_run_task` — pops the per-task `N` (fallback to cache), writes the
  hermes config **before** invoking the hermes subprocess, and sets
  `result["history_turn_count"]` on both success and failure paths.

**Why sliding window (hermes 0.19.1 native) over pre-dispatch summarization:**

- Each loopback iteration has **stable** context (same goal, same project
  state). Summarization would *lose* this context by compressing, while
  sliding-window compaction *keeps* the most recent stable context intact.
- Sliding window is implementation-cheap (no extra LLM call).
  Summarization multiplies tokens by ~50% for marginal benefit on this
  workload pattern.
- hermes 0.19.1 native compaction preserves the cache prefix — a
  summarizer that re-emits a fresh prompt would invalidate the prefix and
  pay full re-prefill on every iteration.

**Predicted impact:** cap the 4x growth in the long tail at ~1.3x
(6 most-recent turns + system prompt, the asymptotic floor). Real data
will land once a post-`c3e998d` task actually runs through the new
wrapper; see `§6` for the verification step.

**Data dependency:** hermes 0.19.1+ (the `compression` config block
shipped in 0.19.0). Production is verified on 0.19.1; the wrapper will
silently no-op on 0.17.x (writes nothing) rather than crash.
