# v1.1.1 — Pre-existing test failure cleanup ticket

**Type**: cleanup / technical debt
**Priority**: medium (not blocking v1.0.1 ship)
**Owner**: TBD
**Source**: 209 pre-existing test failures documented in
`docs/v1.0.1-enroll-update-review.md` §5 (Test status)

---

## Problem

The v1.0.1 milestone ships with 209 pre-existing test failures
that are NOT v1.0.1 regressions — they predate the dashboard
auth requirement and the cookie middleware, and the affected
tests now return 401 from the API. These failures have been
ignored because:

1. The v1.0.1 milestone is functionally complete (13/13 ACs).
2. The pre-existing failures are not v1.0.1 regressions.
3. There's no clear root-cause grouping; tests fail individually
   rather than as a class of issue.

But ignoring them has allowed the failure count to drift without
visibility. The number could be 209 today, 300 next month, 500
in a year, and nobody would notice.

## Goal

Reduce the 209 pre-existing failures to **0** by end of v1.1
cycle, using a strict xfail + issue-ID-per-root-cause approach
that prevents the failure list from becoming a permanent
trash can.

## Approach (strict xfail + issue ID by root cause)

### Step 1: Inventory by root cause (not by test name)

Group the 209 failures by their underlying root cause, not by
which test happens to fail. Expected outcome: ~5-10 distinct
root causes, each covering 10-50+ tests.

Likely root causes based on the v1.0.1 work:

| # | Root cause (working hypothesis) | Estimated tests |
|---|---|---|
| 1 | Tests predate dashboard auth → 401 on `/api/*` | 80-120 |
| 2 | Tests predate cookie middleware → session lookup fails | 20-40 |
| 3 | Sidebar settings card deletions (v3.14.x) → `Models` / `Evaluations` / `Guardrails` lookups fail | 10-20 |
| 4 | Bind-host default change (P0) → tests that assumed `0.0.0.0` bind fail | 5-15 |
| 5 | Onboarding state backfill (P2) → tests that predate `onboarding_state` column fail | 5-10 |
| 6 | Other test rot (mocks, fixtures, imports) | 20-50 |

**Action**: Run pytest with `-v --tb=short` once, group output
by the file:line + the exception message. The hypothesis above
is a starting point; verify with actual output.

### Step 2: File one issue per root cause

For each root cause, file a GitHub issue with:

- **Title**: `v1.1.1 cleanup: <root cause in 5 words>`
- **Body**:
  - Description of the root cause
  - List of affected test files + approximate count
  - One example failing test (the canonical reproducer)
  - Suggested fix (the actual code/test change needed)
  - Acceptance criteria: this issue closes when the listed
    tests all pass without xfail

**Important**: The issue is the unit of work. The xfail
annotation is just a tool to track which tests are blocked on
which issue. Don't file one issue per test.

### Step 3: Annotate with strict xfail

For each affected test, add a one-line annotation in the test
file:

```python
import pytest

@pytest.mark.xfail(
    reason="ISSUE-1234: tests predate dashboard auth → 401 on /api/*",
    strict=True,
)
async def test_foo(client):
    ...
```

The `strict=True` mode is the key:
- If the test still fails → marked as `XFAIL` (expected). No CI
  impact. The xfail annotation is a placeholder for "this is
  known, tracked by ISSUE-1234".
- If the test starts passing (e.g. someone fixes the underlying
  issue) → marked as `XPASS` (unexpected). `strict=True`
  makes this a **test failure**, forcing the author to remove
  the annotation in the same PR that fixed the issue.

This is the difference between xfail and a hardcoded known-
failure list: **xfail actively signals when the problem is
fixed**, a list silently allows drift.

### Step 4: Triage weekly

Each week:
- Count `XFAIL` (still failing as expected) → expected to
  drop
- Count `XPASS` (now passing, strict=True turned into failure)
  → these are fixes! Remove the annotation, close the issue
- Count `FAILED` (real new failures) → triage immediately

The test output `pytest --tb=line -q | grep -E 'XPASS|XFAIL'`
gives the weekly trend. A rising XPASS count is **good** — it
means real fixes are landing. A rising FAILED count is **bad**
— new test rot.

### Step 5: Target = 0 by end of v1.1

The 209 → 0 target is ambitious but achievable because:
- Most root causes are infrastructure (auth, middleware) and
  have well-known fixes (add `await _login(ac, ...)` to test
  fixtures, or pre-`await current_user(request)` to the API
  call being tested).
- The 5-10 root causes are independent — multiple contributors
  can fix them in parallel.
- `strict=True` xfail forces every fix to be visible.

## Why not a hardcoded 209-name baseline list?

Perplexity's review suggested a baseline check
(`test_baseline_known_failures.py` listing the 209 test names).
**Decision (2026-08-09)**: reject the hardcoded list. Reasons:

1. **Maintenance debt from day one**: every test rename, test
   split, or test merge requires updating the list. The list
   becomes a magnet for stale entries.
2. **No signal on fixes**: a hardcoded list treats "209 fails
   expected" as a static fact. If 50 of them get fixed, the
   list still says 209, the CI still passes, and nobody
   notices the wins.
3. **Encourages the trash-can pattern**: future contributors
   see "failures are expected here" and add to the list
   instead of investigating the root cause.

Strict xfail + issue ID is the alternative:
- Annotation lives next to the test it covers (renames are
  co-located in the diff)
- `strict=True` forces every fix to be visible
- The issue tracker is the canonical list of root causes

## Acceptance criteria for this ticket

This ticket (the v1.1.1 cleanup effort) is **done** when:

- [ ] All 209 pre-existing failures are annotated with strict
      xfail + an issue ID
- [ ] At least one root cause is fully fixed (the corresponding
      tests pass, the xfail annotations are removed, the issue
      is closed) — this validates the workflow before scaling
      it to all 209
- [ ] Weekly triage process is documented in
      `docs/v1.1.1-test-cleanup.md` (this file)
- [ ] A `pytest --tb=line -q | grep -E 'XPASS|XFAIL'`
      snapshot is committed to show the current trend
- [ ] The 209 baseline is replaced by a moving count of
      `@pytest.mark.xfail(strict=True)` annotations
