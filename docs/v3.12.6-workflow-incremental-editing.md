# Workflow Incremental Editing Spec (v3.12.6)

Status: Draft
Target milestone: v3.12.6
Owner: Hermes Studio
Scope: Design-time workflow editing for plan editor / workflow editor / chatbox LLM
Non-goal: runtime task dispatch / supervisor behavior

---

## 1. 背景

目前 Visual Plan / Workflow editor 的 LLM 入口，主要是「從頭生成整個 workflow，然後 replace 現有內容」。  
這種模式適合大型重建，但對日常的小改動不理想，例如：

- 在現有 workflow 後面加一個 step。
- 修改某個 step 的 role / action / timeout / output_path。
- 刪除某個已不需要的 step。
- 只想局部調整，不想推翻整個 workflow。

現有 UI 已經有手動操作能力，例如：

- `Add step`
- `Copy / Paste`（clone step）
- `Edit JSON`

但缺少 **LLM 驅動的局部增量修改**。  
因此需要一套 workflow-object level 的 incremental editing 機制，讓 chatbox / assistant 可以對既有 workflow 做 add / edit / remove，而不是每次都 full replace.

## 2. 目標

新增一套 workflow object 的局部編輯能力，支持以下 intent：

- `create_workflow`
- `add_steps`
- `edit_step`
- `remove_step`
- `replace_workflow`

原則：

- 預設是 patch，不是 replace。
- 只修改 design-time workflow object，不影響 runtime tasks。
- 所有 AI 生成的改動都要先顯示 diff preview。
- 用戶確認後才落地。

## 3. 非目標

本 spec 不處理以下事項：

- 不改動 task dispatch / supervisor runtime 行為。
- 不自動更新已 materialize 的 project tasks。
- 不將 workflow edit 直接套用到既有 running project。
- 不做任意 JSON patch / free-form schema mutation。
- 不改現有 full regenerate / replace workflow 流程的語義，只在其旁新增 incremental editing 能力。

## 4. 核心概念

### 4.1 Design-time object coverage

Incremental editing should apply to both:

- `projects.plan_json`
- `workflow_packages.step_template`

Both are design-time objects.  
The UI surface may be different, but the editing model is the same: patch the current template, not the runtime tasks.

### 4.2 Runtime task

Runtime task 指已由 workflow / plan materialize 出來的 project task。  
workflow edit 不得直接修改 runtime task.

### 4.3 Incremental edit

Incremental edit 指在現有 design-time object 上做局部變更，例如：

- append 一個 step.
- patch 某個 step.
- remove 某個 step.

### 4.4 Replace workflow

Replace workflow 指從頭重建整個 workflow object。  
這是明確 destructive action，只能在用戶明確要求時使用。

## 5. UX 原則

### 5.1 Default action

自然語言下的增量修改，預設應該被分類為 **patch**，例如：

- 「加一個 validate-risk step」
- 「把 check-total 改成 quant-reviewer」
- 「刪除舊的 news-research」

這些都應視為 patch，不應默認成 replace.

### 5.2 Replace 只在明確情況出現

只有以下情況，才應預設為 replace：

- 「重新設計整個 workflow」
- 「從頭重建」
- 「用新的方案完全取代現在的 workflow」

### 5.3 Diff preview 必須存在

所有 AI 產生的 workflow 改動，必須在 apply 前顯示 diff preview。  
用戶應能清楚看到：

- 哪些 step 會被新增。
- 哪些 step 會被修改。
- 哪些 step 會被刪除。
- 哪些 step 完全不變。

Diff 必須是 **field-level diff**，不是只有 step-level summary.

### 5.4 明確的 confirmation

apply 之前必須用戶明確確認。  
尤其是 remove / replace / rename 這些破壞性操作，要更清楚提示。

## 6. Supported operations

### 6.1 create_workflow

由 chatbox 或 assistant 生成一個完整 workflow object。  
此操作可作為現有「Generate plan / Create from conversation」的完整生成模式。

### 6.2 add_steps

將一個或多個 step 加入現有 workflow object.

特點：

- 只 append / insert 新 step.
- 不修改既有 step.
- 不動 runtime tasks.

Default behavior:

- If `position` is omitted, append to end.
- `position` may be specified as:
  - `{"after": "<step_name>"}`
  - `{"before": "<step_name>"}`

### 6.3 edit_step

修改指定 step 的欄位，例如：

- `agent_role`
- `action`
- `depends_on`
- `feedback_to`
- `params_template`
- `timeout_seconds`
- `retry`
- `max_retries`
- `output_path`

特點：

- 預設不支援 silent rename.
- 需要明確指定目標 step.
- `output_path` must remain under the project temp folder after path normalization; path traversal must be rejected.
- 修改完成後要通過 validation.

### 6.4 remove_step

刪除指定 step.

特點：

- 要檢查是否有其他 step 引用它.
- 預設拒絕靜默刪除仍被引用的 step.
- 如需 rewiring references，必須明確要求並在 preview 顯示影響.
- DELETE request does **not** require a reason parameter; server may attach a default audit reason.

### 6.5 replace_workflow

用完整 workflow object 替換現有 workflow object.

特點：

- 只用於明確重建整體 workflow 的情況.
- 要高亮警告，因為可能移除大量 step.
- 保留 current full replace 行為，不破壞舊流程.

## 7. Intent mapping

chatbox / assistant 必須將自然語言對應到以下 intent 之一：

| User intent | Mapped operation |
|---|---|
| 「加一個 step」 | `add_steps` |
| 「把某 step 改成…」 | `edit_step` |
| 「刪掉某 step」 | `remove_step` |
| 「完整重寫 workflow」 | `replace_workflow` |
| 「從頭做一個 workflow」 | `create_workflow` |

### 7.1 Mixed operations

Mixed operations in one chat round-trip are allowed and should be **atomic**:

- add + edit
- edit + remove
- add + remove
- add + edit + remove

Example structured patch payload:

```json
{
  "type": "apply_workflow_patch",
  "patch": {
    "add": [
      {
        "name": "validate-risk",
        "agent_role": "risk-analyst",
        "depends_on": ["summarize-ip-results"]
      }
    ],
    "edit": [
      {
        "name": "check-total",
        "patch": {
          "agent_role": "quant-reviewer",
          "timeout_seconds": 2400
        }
      }
    ],
    "remove": ["news-research"]
  },
  "reason": "Add risk validation, update review role, remove stale research step."
}
```

### 7.2 Ambiguous input

如果語句同時可能是 patch 或 replace，例如：

- 「幫我優化下整個 workflow」
- 「改好啲」

應先問澄清問題，不應自動 replace.

## 8. API design

建議採用 domain-specific endpoint，而不是通用 JSON patch.

### 8.1 Add steps

```http
POST /api/workflows/{workflow_id}/steps
```

Request body:

```json
{
  "steps": [
    {
      "name": "validate-risk",
      "agent_role": "risk-analyst",
      "action": "do_task",
      "depends_on": ["build-model"],
      "feedback_to": [],
      "params_template": {},
      "timeout_seconds": 1800
    }
  ],
  "position": {
    "after": "build-model"
  },
  "reason": "Add a risk validation step after model building."
}
```

### 8.2 Edit step

```http
PATCH /api/workflows/{workflow_id}/steps/{step_name}
```

Request body:

```json
{
  "patch": {
    "agent_role": "quant-reviewer",
    "timeout_seconds": 2400
  },
  "reason": "Need a different reviewer and longer timeout."
}
```

### 8.3 Remove step

```http
DELETE /api/workflows/{workflow_id}/steps/{step_name}
```

### 8.4 Replace workflow

```http
PUT /api/workflows/{workflow_id}
```

or use existing replace endpoint if already present.  
This operation retains current semantics.

## 9. Validation rules

### 9.1 Step names

- `add_steps` 中新 step name 不可與現有 step collision.
- 如 collision，應回 `409 Conflict`.
- 不應 silent rename.

### 9.2 References

- `depends_on` 必須引用已存在 step.
- `feedback_to` 必須引用已存在 step.
- 若引用不存在，應回 `422 Unprocessable Entity`.
- 不應像 LLM full-generation 那樣靜默 drop reference.

### 9.3 DAG integrity

每次 add / edit / remove 後，都必須驗證：

- no cycle.
- no dangling reference.
- 依賴關係仍可形成合法 DAG.

### 9.4 Remove constraints

刪除 step 前要檢查：

- 有沒有其他 step 引用它.
- 若有，預設拒絕.
- 若用戶要求 rewiring，必須在 preview 明確顯示影響.

### 9.5 Rename handling

v1 不支援 silent rename.  
If rename is needed:

- it must be a separate explicit operation.
- it must rewrite all references.
- it must show a diff preview.
- if not explicitly requested, do not infer rename from edit_step.

## 10. UI / chatbox flow

### 10.1 現有 UI 保留

現有手動工具保留不變：

- Add step
- Copy / Paste
- Edit JSON
- Save
- Save as workflow
- Generate plan

### 10.2 新增 AI patch flow

在 chatbox assistant 中新增「patch mode」：

- `Apply as patch`
- `Apply as new plan` / `Replace workflow`

預設應突出 patch，不應突出 replace.

### 10.3 Diff preview

AI 產生的 patch 應顯示：

- ADD / EDIT / REMOVE 的 step 列表.
- 每個 modified step 的 field-level diff.
- 受影響的 references.
- 會否引發 DAG warning.

### 10.4 Context-aware editing

當用戶選中某個 node 時，chatbox 應自動帶入該 node context.  
Context lifetime:

- tied to current chatbox session.
- stored in sessionStorage or equivalent client-side session state.
- cleared on tab close / refresh.

Example:

- 選中 `summarize-ip-results`
- 輸入：「後面加一個 validate-risk」

系統應優先理解成對該 node 的增量修改.

### 10.5 Stale draft TTL

Ambiguous patch drafts should expire.  
Recommended TTL:

- 24 hours

After expiry:

- patch draft auto-expires.
- audit log records `patch.draft_expired`.
- chatbox opens cleanly without stale draft state.

---

## 11. Audit / history

每次 workflow-object 變更都應寫 audit log：

- actor
- timestamp
- operation type (`create_workflow` / `add_steps` / `edit_step` / `remove_step` / `replace_workflow`)
- before snapshot
- after snapshot
- diff summary
- user reason / prompt

For DELETE operations:

- if no explicit user reason is provided, server may write a default reason such as:
  - `removed by LLM (no user reason provided)`

## 12. Example flows

### 12.1 Add a step

User:

> 在 summarize-ip-results 後面加一個 validate-risk step，role 用 risk-analyst。

Mapped to:

- `add_steps`

Effect:

- 新增 `validate-risk`
- `depends_on=["summarize-ip-results"]`
- 其他 step 不變

### 12.2 Edit a step

User:

> 將 check-total 的 role 改成 quant-reviewer，timeout 改成 20 分鐘。

Mapped to:

- `edit_step`

Effect:

- 只 patch `check-total`
- 不改其他 step

### 12.3 Remove a step

User:

> 刪除舊的 news-research。

Mapped to:

- `remove_step`

Effect:

- 若仍被引用，先拒絕並提示引用關係
- 若無引用，才刪除

### 12.4 Replace workflow

User:

> 重新設計整個 workflow，用 5 個 step 取代現在的流程。

Mapped to:

- `replace_workflow`

Effect:

- 整個 workflow 重寫
- 顯示高風險 warning

## 13. Implementation notes

### 13.1 Reuse existing models

可重用：

- `PlanStep`
- workflow package schema
- existing dependency resolver
- existing audit framework

### 13.2 Separate from task layer

workflow-object edit 絕不應直接觸發：

- task archive
- task dispatch
- task reset
- loopback logic

### 13.3 Preserve existing replace behavior

現有 full regenerate / replace flow 不應壞掉。  
Incremental editing 應是新增能力，不是重構整個舊模型。

### 13.4 Path safety

Any editable file system path such as `output_path` must be validated:

- normalize path
- reject traversal
- require project temp folder boundary

---

## 14. Open questions resolved

1. `rename_step` v1 不做.
2. `remove_step` 不做 automatic rewiring，只做 explicit.
3. `add_steps` default append，optional `position`.
4. Mixed operations in one patch are allowed, atomic.
5. Workflow revision history UI v1 不做，audit log 足夠.

---

## 15. Recommended v1 scope

我建議第一版只做：

- `add_steps`
- `edit_step`
- `remove_step`
- patch preview
- diff confirmation
- 保留 full replace 作為明確 action
- `apply_workflow_patch` suggestion type for chatbox
- session-scoped context selection
- stale patch TTL

暫時唔做：

- silent rename
- automatic rewiring
- 任意 JSON patch
- 把 workflow edit 套用到 runtime tasks
- dedicated revision history UI
