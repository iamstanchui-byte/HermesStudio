# 3-Tier Memory Design

> **Status**: design spec (not yet implemented)
> **Inspired by**: [HKUDS/DeepTutor](https://github.com/HKUDS/DeepTutor) — 3-layer memory workbench (L1 traces, L2 surface summaries, L3 synthesis)
> **Scope**: hermes-orchestrator's project-level memory so new tasks can see what prior work has been done in a project without manual point-and-click

---

## Why this exists

**Problem**: When the user runs `proj-c1e7286e` (analyze the 2026 World Cup final), the LLM planner generated a generic plan with `fetch_win_stats historical_win_rate` — which doesn't exist for a future game. The first plan failed; the second plan succeeded with `browser_fetch_teams` + `ridge_predict_winrate` + `yuanbao_analyze`. The second plan **did not reference the first plan's results** even though both were working on the same project.

**Symptoms**:
- New tasks don't know what prior tasks already did
- Replan starts from scratch, doesn't reuse prior work
- Coord agent has to rediscover context each iteration
- Old task results live in DB but are hard to surface

**Goal**: New tasks see what's been done, what files exist, what data is available, what the coord has decided — automatically, without the user manually pointing to prior reports.

---

## Architecture: 3 Tiers

### L1 — Append-only event trace
- **Format**: JSONL (one event per line)
- **Immutable**: never modified after write
- **Path per project**: `<project_dir>/trace.jsonl`
- **Path global**: `~/hermes-orchestrator/memory/trace.jsonl`
- **Schema**:
  ```json
  {"ts": "2026-07-19T02:11:54+08:00", "event_type": "project.plan_generated", "actor": "supervisor", "project_id": "proj-c1e7286e", "task_id": null, "payload": {"task_count": 5, "planner": "llm"}}
  ```
- **Mirrored from**: every row in `audit_log` table
- **Used for**: human audit, debugging, future re-derivation of L2/L3
- **Injected into task prompts**: NO (too verbose / too raw)

### L2 — Curated facts (per project / per user)
- **Format**: Markdown with structured sections
- **Editable**: auto-appended by supervisor + human-editable via dashboard
- **Path per project**: `<project_dir>/facts.md`
- **Path per user**: `~/hermes-orchestrator/memory/profile.md`
- **Schema**:
  ```markdown
  # Project Facts: <name>

  > Auto-curated from L1 (trace.jsonl). Human-editable.
  > Each fact cites a L1 event_id for traceability.

  ## Goal
  [cite:event_id@timestamp] goal text

  ## Plan History
  [cite:event_id@timestamp] Plan N (date): task list — outcome

  ## Task Results
  [cite:event_id@ts] <task_id> <name> (role, date) -- 1-line summary

  ## Key Findings
  [cite:event_id@ts] finding

  ## Files (artifacts)
  [cite:event_id@ts] filename (size, date) -- description

  ## Coord Verdicts
  [cite:event_id@ts] Plan N Iter M: DECISION: PASS/FAIL -- reason
  ```
- **Auto-appended by supervisor on**:
  - `task.completed` → `## Task Results` section
  - `plan_generated` → `## Plan History` section
  - `iteration_completed` → `## Coord Verdicts` section
  - `artifact_uploaded` (new event type) → `## Files` section
- **Used for**: new task context injection, coord review, replan modal display
- **Injected into task prompts**: YES (last 4KB)

### L3 — Cross-surface synthesis (Phase 2)
- **Format**: Markdown, structured sections
- **Generated by LLM** (consolidator) from L2 facts
- **Path per project**: `<project_dir>/state.md`
- **Path per user**: `~/hermes-orchestrator/memory/recent.md`
- **Schema**:
  ```markdown
  # Project State: <name>

  > LLM-generated synthesis from L2 (facts.md).
  > Last regenerated: <ts> by <trigger>.
  > Cites L2 fact_ids.

  ## Goal
  [facts:goal@ts] goal text

  ## Current Status
  - State: <planning|running|completed>
  - Plan: N (generated <ts>)
  - Iter: M / max_iterations
  - Deliverable: <filename> (<size>)

  ## Open Questions
  [facts:key-findings@ts] data gap or issue
  - suggested next step

  ## Key Findings (synthesized)
  - finding (cited from [facts:...])

  ## Next Steps (if iter resumes)
  1. step (cited from [facts:...])
  ```
- **Regenerated by supervisor on**: every `iteration_completed`
- **Used for**: high-level "what's the current state" view, fast task orientation
- **Injected into task prompts**: YES (first 2KB, prepended to L2)

## Hook Points (when to write each tier)

### L1 writes — every audit event
- **Where**: in `core/audit.py::audit_log()` (or wrap with new `core/memory.py::trace_log()`)
- **How**: insert row to `audit_log` (existing) AND append line to JSONL
- **Atomicity**: append-only JSONL is naturally atomic per line on POSIX; on Windows, use `os.open(O_APPEND)` + fsync
- **Performance**: <1ms per event, no impact on hot path

### L2 writes — supervisor on specific events

| Event | L2 section | Auto-line format |
|---|---|---|
| `task.completed` | `## Task Results` | `- [cite:<task_id>@<ts>] <name> (<role>, <ts>) -- <1-line summary>` |
| `plan_generated` | `## Plan History` | `- [cite:plan_generated@<ts>] Plan N: <N> tasks (<action list>) -- outcome` |
| `iteration_completed` | `## Coord Verdicts` | `- [cite:iter@<ts>] Plan N Iter M: DECISION: <verdict> -- <reason>` |
| artifact uploaded (new event) | `## Files` | `- [cite:upload@<ts>] <filename> (<size> bytes, <ts>) -- <rel path>` |
| `project.created` | `## Goal` | `- [cite:created@<ts>] <goal text>` |
| `project.replan_requested` | (append) | `- [cite:replan@<ts>] Replan: new goal preview=<...>` |

- **Where**: new module `core/memory.py::append_fact(project_id, section, text, cite_id)`
- **Template bootstrap**: when `project.created`, write initial `facts.md` with header + Goal section
- **Size cap**: 8KB per `facts.md`; auto-archive older entries to `<project_dir>/facts_archive.md` when exceeded (use FIFO rotation)

### L3 writes — LLM synthesis (Phase 2)
- **Where**: `core/memory.py::regenerate_state(project_id)`
- **When**: after `iteration_completed`
- **LLM call**: small prompt → input L2 facts.md (last 8KB) → output structured state.md
- **Cost**: ~500 tokens per regen, ~6 regens per project, ~3K tokens per project lifetime
- **Cache**: store last state.md in `state_prev.md` for diff visibility

## Injection Points (when to read each tier)

### L1 (trace.jsonl) — never injected
- L1 is for human audit + future re-derivation only
- Too verbose, too raw, too noisy for LLM context

### L2 (facts.md) — injected into task prompts (Phase 1)
- **Where**: `agent_cli.py::_run_task()` (after building task prompt, before invoking hermes)
- **How**:
  ```python
  # Inject last 4KB of facts.md as [Project Memory] section
  facts_path = Path(profile_root) / ".." / ".." / f"{project_id}" / "facts.md"
  if facts_path.exists():
      facts_text = facts_path.read_text(encoding="utf-8")
      if len(facts_text) > 4096:
          facts_text = "...[earlier entries truncated]...\n" + facts_text[-4096:]
      prompt += f"\n\n--- PROJECT MEMORY ---\n{facts_text}\n--- END PROJECT MEMORY ---\n"
  ```
- **Coord task**: same injection, but use full facts.md (no truncation)
- **Replan modal**: fetch `facts.md` content via API or read from disk, show in collapsible "📋 Project memory" section

### L3 (state.md) — prepended to task prompts (Phase 2)
- **Where**: same place as L2, but prepended
- **How**: read `state.md` (first 2KB) → inject as `[Project State]` section ABOVE `[Project Memory]`

## Concrete Use Cases

### UC1: New task starts (Phase 1)
```
Task: "fetch_squad_injuries" (win-agent01, depends_on=[t-7a29ee59])
Wrapper reads:
  <project_dir>/facts.md  (4KB tail)

Injects into prompt:
  --- PROJECT CONTEXT ---
  LOCAL WORKING DIR: ...
  (use file tools to read/write files here.)

  --- PROJECT MEMORY ---
  # Project Facts: World Cup 2026

  ## Goal
  [cite:created@02:10] Analyze 2026 World Cup final 2 teams' win rate + team personnel

  ## Plan History
  [cite:plan_generated@02:11] Plan 1: 5 tasks (scrape_bracket, fetch_win_stats x2, ...) — FAILED
  [cite:plan_generated@13:21] Plan 2: 5 tasks (browser_fetch_teams, browser_fetch_squads, ...) — succeeded

  ## Task Results
  [t-d4432279] Find 2026 final teams -- Spain vs Argentina
  [t-7a29ee59] fetch squad personnel status -- empty (no upstream data)
  [t-79d47af8] ridge predict -- P(Arg) 0.51-0.54, P(Spa) 0.46-0.49
  [t-201ee661] summarize final report -- summary_v2.md 11KB

  ## Key Findings
  Spain 50.0% / Arg 56.8% all-time WC win rate
  Data gap: no injury list, no starting XI, no xG

  ## Files
  summary_v2.md (11KB) — 2nd run, with Ridge prediction
  --- END PROJECT MEMORY ---

Agent decides: "t-7a29ee59 tried browser_fetch_squads and got empty. Let me try a different data source — maybe news articles with team rosters."
```

### UC2: Coord review (Phase 1)
- Coord task gets full `facts.md` (no truncation) in its action text
- Coord reads [Coord Verdicts] section to see prior decisions
- Coord writes back: `## Coord Verdicts` append with new verdict

### UC3: Replan modal (Phase 1)
- Replan modal shows current `facts.md` in a collapsible "📋 Project memory" section
- User sees what's been done before writing new goal
- Sample UI:
  ```html
  <details>
    <summary>📋 Project memory (4.2 KB, 12 facts)</summary>
    <pre>...</pre>
  </details>
  ```

### UC4: User audit (Phase 1, after-the-fact)
- User can read `<project_dir>/trace.jsonl` directly (JSONL, line-by-line)
- Filter: `Get-Content trace.jsonl | Where-Object { $_ -match "iter" }`
- Export: `trace.jsonl | ConvertFrom-Json | Export-Csv`

## Size Limits & Rotation

| File | Cap | When exceeded |
|---|---|---|
| `facts.md` | 8 KB | Auto-archive older entries to `facts_archive.md` (FIFO) |
| `state.md` | 2 KB | Just keep latest; archive old versions to `state_archive/2026-07-19T13-33.md` |
| `trace.jsonl` | unlimited | Split monthly: `trace/2026-07.jsonl` (optional, Phase 3) |
| `profile.md` (user) | 4 KB | Manual trim, with audit log entry |
| `recent.md` (user) | 4 KB | Auto-trim to last 7 days |

## API Endpoints (Phase 1+)

| Method | Path | Purpose |
|---|---|---|
| `GET` | `/api/projects/{id}/memory/facts` | Return `facts.md` content + size + last_modified |
| `GET` | `/api/projects/{id}/memory/trace?since=<iso>` | Return filtered trace.jsonl entries |
| `PATCH` | `/api/projects/{id}/memory/facts` | Append a human-edited fact (auth: operator) |
| `POST` | `/api/projects/{id}/memory/state/regenerate` | Manually trigger L3 regen (Phase 2) |
| `GET` | `/api/memory/profile` | User-level profile (Phase 3) |
| `GET` | `/api/memory/recent` | User-level recent activity (Phase 3) |

## Open Questions

1. **Should L1 include raw hermes stdout/stderr?** Currently `audit_log` doesn't (too verbose). Probably not for now; if needed, future work.
2. **Should L2 be per-surface (per profile/role) or per-project?** DeepTutor uses per-surface. We use per-project for simplicity; can refactor later.
3. **How to handle plan replans?** When replan happens, old L2 entries are still valid (they describe what was done). Just append new plan entry, don't delete old.
4. **Should agents be able to read each other's L2 (cross-profile)?** Yes, all agents in a project see the same project facts.
5. **For user-level profile.md, who edits it?** Phase 3: auto-curator LLM (proposes facts) + human override.
6. **Should we expose facts.md as a writable UI?** Yes, PATCH endpoint. Also a "✏️ Edit facts" button on project page.

## Why 3 tiers, not 1

- **Single file (only L2)**: easy to write, hard to verify. Can claim "Spain 50% won rate" but where did it come from? No audit trail.
- **3 tiers (L1+L2+L3)**: L1 immutable gives audit trail. L2 curated is editable but cites L1. L3 synthesized gives high-level view but cites L2. Any claim can be traced back through 2 hops to a raw event.
- **DeepTutor's insight**: making memory **inspectable** (not a hidden vector store) is what makes it trustworthy. Users can read it, audit it, edit it.

## Reference: DeepTutor's 3-layer memory

From https://github.com/HKUDS/DeepTutor README:

> **🧠 Memory — Inspectable Personalization**
>
> Memory is a file-backed, three-layer system you can read, curate, and audit — deliberately *not* a hidden vector store.
> - **L1** is the workspace mirror plus an append-only event trace (`trace/<surface>/<date>.jsonl`)
> - **L2** is per-surface curated facts (`L2/<surface>.md`)
> - **L3** is cross-surface synthesis (`L3/<profile|recent|scope|preferences>.md`)
> - Because L2 cites L1 and L3 cites L2, nothing in your profile is unaccountable.
>
> The Memory Graph shows the whole pyramid — L3 synthesis at the centre, L2 in the middle ring, L1 traces on the outside — so you can trace any synthesized claim back to the exact raw event behind it.

Our adaptation:
- Per-project instead of per-surface (our project is the unit of work)
- L1 is JSONL (DeepTutor uses same)
- L2 is single file per project (we don't have 7 surfaces; we have one project)
- L3 is one file per project (instead of profile/recent/scope/preferences)

## What "successful" looks like

**User replans `proj-c1e7286e` with new goal**:
- Modal shows current `facts.md` — "Plan 1 failed, Plan 2 succeeded with Ridge + qualitative. summary_v2.md exists. Data gap: no injury/lineup."
- User sees "OK, I should add 'find betting odds' to my new goal since injury data is missing"
- New plan respects prior: tasks read summary_v2.md to extract current findings, then add odds lookup
- Coord agent in iter 1 has full context: "Plan 1 failed, Plan 2 succeeded, now we add odds"

**User starts new project (Phase 3)**:
- profile.md shows user preferences (e.g., "prefers Ridge ensemble, dislikes SQL queries, uses zh-HK for summaries")
- recent.md shows last 7 days (e.g., "5 projects: 2 MT5 trading, 2 research, 1 tool dev")
- New project planner uses these signals

**User audits a project months later**:
- Opens project, sees `facts.md` (curated) + `state.md` (synthesis)
- Click "View trace" → JSONL stream of every event, filter by type/actor/date
- Click "Cite" on a finding → jumps to L1 event that produced it
