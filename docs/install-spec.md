# Hermes Orchestrator — Install Spec

> Productize-time spec. The current dev workflow (`pip install -e ".[dev]"` from a clone) is **not** what end users see.

**Audience**: semi-technical Windows users (NOT developers). The installer must be one double-click, one UAC prompt, one config screen, then "open in browser".

**Platform target**: Windows 10/11 (64-bit). Linux is out of scope for v1.0 of the product.

---

## 1. Install mode decision

**Decision: per-machine install.** Reasons:

| | Per-user (AppData) | Per-machine (Program Files) |
|---|---|---|
| Admin needed for install | ❌ | ✅ (one UAC) |
| Survives logout / reboot while server runs | ❌ | ✅ |
| Multi-user on same box share one server | ❌ | ✅ |
| Service can run before any user logs in | ❌ | ✅ |
| Uninstall cleanly removes everything | ❌ (config scattered in profile) | ✅ (everything in known places) |

Hermes Orchestrator is a **server** that drives local agents — it should keep running for all users regardless of who is logged in. Per-user install is wrong for this product.

The wizard does **not** ask "per-user or per-machine". It always goes per-machine. (A power user can still clone the repo and `pip install -e` for dev work.)

---

## 2. Layout on disk

Standard Windows server pattern. Three roots:

```
C:\Program Files\HermesOrchestrator\              # read-only, all users
├── hermes_orch\                                  # python package (from src/)
├── .venv\                                        # venv created at install time
├── bin\hermes-orch.exe                           # PyInstaller-built launcher (optional)
├── service\install_service.ps1                   # service installer script
├── service\uninstall_service.ps1
├── service\hermes-orch-service.exe               # NSSM-wrapped launcher
├── LICENSE
├── README.txt                                    # short pointer, not the full doc
└── uninstall.exe                                 # generated by installer

C:\ProgramData\hermes-orchestrator\              # shared state, all users
├── hermes-orch.db                                # SQLite (projects, agents, audit)
├── projects\                                     # shared project storage
├── audit.log                                     # daily-rotated
└── service-config.yaml                           # non-secret service config (port, paths, etc.)

C:\Users\<user>\AppData\Roaming\hermes-orchestrator\   # per-user
├── config.yaml                                   # LLM API key, agent aliases (per user)
└── logs\
    └── last-7-days-rotated
```

**Per-user override hierarchy** (standard):
1. `%APPDATA%\hermes-orchestrator\config.yaml` (per user)
2. `C:\ProgramData\hermes-orchestrator\service-config.yaml` (shared service-level)
3. `C:\Program Files\HermesOrchestrator\.venv\...` defaults baked into the package

Per-user wins for any key it sets. Service-level wins for shared settings (port, db path, project storage root). This lets each user have their own LLM key without fighting over the same file.

## 3. Service account

**Default: `NT AUTHORITY\LocalSystem`** for v1.0. Reasoning:

- ✅ Zero setup, no user lookup
- ✅ Survives "no user logged in" scenarios
- ✅ Reads `%APPDATA%\<user>\config.yaml` for the LLM key when the dashboard user is logged in
- ⚠️ Broad privileges — but the orchestrator is the only thing running as it, and it doesn't shell out untrusted input
- ⚠️ LocalSystem can't access network shares as a remote user (no SMB impersonation) — for v1.0 this is fine, we don't use network shares

**Future option (post v1.0)**: dedicated `hermes-svc` account. LocalSystem is good enough for now and saves a chunk of installer complexity.

**Service recovery**: restart on failure, 5s delay, 3 attempts. Then give up and wait for next manual trigger (Task Scheduler watchdog, which is installed alongside the service).

## 4. Pre-install checks (silent)

Installer must verify before showing any UI:

| Check | Why | Fail behaviour |
|---|---|---|
| Windows ≥ 10.0.17763 | Server side needs Win10 1809+ | block with message |
| Admin token present | Need to write to Program Files + create service | block with UAC re-elevation prompt |
| Python 3.10+ available OR bundled launcher | Run the server | block if no Python AND no bundled binary |
| Port 8765 free | Default listen port | warn, allow override |
| ≥ 200 MB disk free | Venv + DB + projects | block |
| No existing service with same name | Clean upgrade | block with "uninstall first" |
| `C:\ProgramData\hermes-orchestrator\` writable | Create dirs | block |

**Bundled Python or installed Python?** Two product SKUs:
- **Light installer**: 40 MB, requires Python 3.10+ on PATH (let user install python.org if missing)
- **Fat installer**: 120 MB, bundles Python embeddable + venv, no system Python needed

**Default to light**. Document "install Python 3.10+ from python.org" in pre-flight. If they want a no-fuss install, ship a fat variant later.

## 6. Install steps (the actual work)

Sequence after Install button is clicked:

1. **Create dirs**:
   - `C:\Program Files\HermesOrchestrator\`
   - `C:\ProgramData\hermes-orchestrator\projects\`
2. **Copy payload**: source files → install dir (skip `.git`, `tests/`, `docs/`, `*.pyc`, `__pycache__/`, `.venv/`)
3. **Create venv** at `C:\Program Files\HermesOrchestrator\.venv\`:
   - `python -m venv .venv`
   - `.venv\Scripts\pip install --upgrade pip wheel`
   - `.venv\Scripts\pip install -e .` (or `pip install .` for wheel)
   - `.venv\Scripts\pip install nssm` (for service wrapper)
4. **Bootstrap service config** at `C:\ProgramData\hermes-orchestrator\service-config.yaml`:
   ```yaml
   orchestrator:
     host: 127.0.0.1
     port: 8765
     db_path: C:\ProgramData\hermes-orchestrator\hermes-orch.db
   projects:
     storage_root: C:\ProgramData\hermes-orchestrator\projects
   logging:
     audit_log_path: C:\ProgramData\hermes-orchestrator\audit.log
   auth:
     hmac_timestamp_tolerance_seconds: 300
   supervisor:
     poll_interval_seconds: 5
   cleanup:
     retention_days: 30
     daily_sweep: true
   llm:
     mock: true   # user fills in their key on first run
     provider: minimax
   ```
5. **Install service** via NSSM:
   - `nssm install HermesOrchestrator "C:\Program Files\HermesOrchestrator\.venv\Scripts\python.exe"`
   - args: `-m hermes_orch serve --no-reload --host 127.0.0.1 --port 8765`
   - working dir: `C:\Program Files\HermesOrchestrator\`
   - stdout/stderr → `C:\ProgramData\hermes-orchestrator\logs\service.out.log`
   - env: `USERPROFILE=C:\Windows\system32\config\systemprofile` is fine because all paths are absolute; service reads config from `C:\ProgramData\`
6. **Set service recovery**: `sc failure HermesOrchestrator reset= 5 actions= restart/5000/restart/5000/restart/5000`
7. **Install Task Scheduler watchdog** (as LocalSystem, every 1 min, same script we already use in dev):
   - Polls `http://127.0.0.1:8765/api/health`
   - If down → `Start-Service HermesOrchestrator`
   - This is the same `watchdog-hermes.ps1` we shipped in v2.x dev, lifted to Program Files
8. **Start service**: `Start-Service HermesOrchestrator`
9. **Smoke test**: poll `http://127.0.0.1:8765/api/health` for up to 30s, fail loud if not 200
10. **Optional**: open browser to dashboard (if user checked the box)

---

## 7. First-run wizard (browser, on dashboard)

When user opens `http://localhost:8765/` for the first time:

1. **Welcome screen** with "Get started" CTA
2. **LLM provider picker** (default `minimax`, alternatives: openai, anthropic, custom OpenAI-compatible)
3. **API key input** (password field, never displayed back, stored in `%APPDATA%\hermes-orchestrator\config.yaml` with restrictive ACL)
4. **Test connection** button → POST to LLM, show "Connected to `<model>`" or error
5. **Save** → writes config.yaml, sets `llm.mock: false` in service-config.yaml, restarts service (or hot-reloads if v1.0 supports it)
6. **Add agent host** → show `wrappers\hermes-orch-agent` install instructions + a one-liner the user runs on each agent host
7. **Done** → redirect to `/agents` dashboard

This is the part that hides "JSON / agent_role / depends_on" from the user. They never see those words unless they go looking.

## 8. Agent host install (separate product, but bundled)

Agent hosts (the boxes that run hermes-agent) get their own simpler installer. The orchestrator already provides the wrapper CLI (`hermes_orch.agent_cli`) — the agent host install is just "put it on the box, point it at the orchestrator, autostart it".

Shared requirements (both platforms):
- Python 3.10+
- The `hermes-orch-agent` CLI (same PyPI package, `pip install hermes-orchestrator[agent]`)
- An HMAC key shared with the orchestrator (generated on dashboard, copy-paste into agent config)
- A "register with orchestrator at `<orchestrator-ip>:8765`" step
- Network reachability to the orchestrator on port 8765 (or whatever port the user chose)

For v1.0 agent hosts are on the same LAN as orchestrator (the user types `http://192.168.1.x:8765` in agent setup). v2.0+ would add a tunnel.

### 8.1. Windows agent install

GUI installer (`hermes-orch-agent-setup.exe`). Same installer framework as the orchestrator. No service, just a Task Scheduler task that runs the wrapper as the logged-in user (so it has access to user-mode stuff like their IDE config etc).

Wizard asks for:
- Orchestrator URL (`http://192.168.1.x:8765`)
- HMAC shared secret (paste from dashboard)
- Agent hostname (default: `win-<hostname>`)
- This host's profile names (multi-select: super, super-b, win-agent01, etc., or "use defaults")

Install steps:
1. `pip install hermes-orchestrator[agent] --user`
2. Write `%APPDATA%\hermes-orchestrator\agent.yaml` with orch URL + HMAC key
3. Register Task Scheduler task `hermes-orch-agent-<hostname>` that runs `python -m hermes_orch.agent_cli run --config <path>` at logon
4. Smoke test: send a heartbeat, verify orchestrator dashboard shows "online"

### 8.2. Linux agent install (v1.0 supported)

Headless install — no GUI on most Linux agent boxes. Two paths: a single bash one-liner, or step-by-step for users who want to see what happens.

**Prereqs** (one-time on the host):
```bash
sudo apt install -y python3.11 python3.11-venv python3-pip  # Debian/Ubuntu
# or: sudo dnf install -y python3.11   # Fedora/RHEL
```

**One-liner (recommended for non-tech users)**:
```bash
curl -sSL https://hermes-orchestrator.example.com/install-agent.sh | bash -s -- \
    --orchestrator http://192.168.1.x:8765 \
    --hmac-secret "paste-from-dashboard-here" \
    --hostname "linux-$(hostname -s)"
```

The script does, in order:
1. Detect distro + Python version
2. Create system user `hermes-agent` (no shell, no home — service account)
3. `python3.11 -m venv /opt/hermes-orchestrator-agent/.venv`
4. `/opt/hermes-orchestrator-agent/.venv/bin/pip install hermes-orchestrator[agent]`
5. Write `/etc/hermes-orchestrator/agent.yaml` (root-owned, mode 0600):
   ```yaml
   orchestrator:
     base_url: http://192.168.1.x:8765
     hmac_secret: <paste from dashboard>
   agent:
     hostname: linux-...
     profiles: [super, super-b]   # default
   ```
6. Install systemd unit `/etc/systemd/system/hermes-orch-agent@.service`:
   ```ini
   [Unit]
   Description=Hermes Orchestrator Agent (%i)
   After=network-online.target
   Wants=network-online.target

   [Service]
   Type=simple
   User=hermes-agent
   Group=hermes-agent
   Environment=HERMES_AGENT_PROFILE=%i
   ExecStart=/opt/hermes-orchestrator-agent/.venv/bin/python -m hermes_orch.agent_cli run \
       --config /etc/hermes-orchestrator/agent.yaml \
       --profile ${HERMES_AGENT_PROFILE}
   Restart=always
   RestartSec=5
   StandardOutput=journal
   StandardError=journal
   # Hardening
   NoNewPrivileges=true
   ProtectSystem=strict
   ProtectHome=true
   ReadWritePaths=/var/lib/hermes-orchestrator-agent
   PrivateTmp=true

   [Install]
   WantedBy=multi-user.target
   ```
7. Enable + start the default profile instances:
   ```bash
   sudo systemctl daemon-reload
   sudo systemctl enable --now hermes-orch-agent@super.service hermes-orch-agent@super-b.service
   ```
8. Smoke test: `systemctl status hermes-orch-agent@super` → should show "active (running)" + recent heartbeat in journal

**Manual / step-by-step** (if user wants to see what the script does):
```bash
# 1. system user
sudo useradd --system --shell /usr/sbin/nologin --home-dir /var/lib/hermes-orchestrator-agent hermes-agent

# 2. venv + install
sudo mkdir -p /opt/hermes-orchestrator-agent
sudo python3.11 -m venv /opt/hermes-orchestrator-agent/.venv
sudo /opt/hermes-orchestrator-agent/.venv/bin/pip install --upgrade pip wheel
sudo /opt/hermes-orchestrator-agent/.venv/bin/pip install "hermes-orchestrator[agent]"

# 3. config
sudo mkdir -p /etc/hermes-orchestrator
sudo tee /etc/hermes-orchestrator/agent.yaml >/dev/null <<'YAML'
orchestrator:
  base_url: http://192.168.1.x:8765
  hmac_secret: REPLACE_ME
agent:
  hostname: linux-myhost
  profiles: [super, super-b]
YAML
sudo chmod 0600 /etc/hermes-orchestrator/agent.yaml

# 4. systemd unit (same content as above)
sudo tee /etc/systemd/system/hermes-orch-agent@.service >/dev/null <<'UNIT'
... (same as in one-liner) ...
UNIT

# 5. activate
sudo systemctl daemon-reload
sudo systemctl enable --now hermes-orch-agent@super hermes-orch-agent@super-b

# 6. verify
sudo systemctl status hermes-orch-agent@super
sudo journalctl -u hermes-orch-agent@super -f
```

**Template unit on disk** (for the PyPI package): ship `/opt/hermes-orchestrator-agent/.venv/lib/python3.11/site-packages/hermes_orch/agent/contrib/hermes-orch-agent@.service`. The install script copies it to `/etc/systemd/system/`.

**Why templated (`@.service`)**:
- One unit file → many instances (one per profile)
- `systemctl enable hermes-orch-agent@super` starts the "super" profile
- `systemctl enable hermes-orch-agent@win-agent01` starts the "win-agent01" profile
- All instances share the unit config; only `HERMES_AGENT_PROFILE` differs

**Why `Restart=always` + `RestartSec=5` (no separate watchdog)**:
- systemd itself restarts the process if it dies
- No Task Scheduler equivalent needed
- One less moving part than Windows

**Logs**: `sudo journalctl -u hermes-orch-agent@super -f` (no separate log file; journald handles rotation). User can also enable persistent storage: `sudo mkdir -p /var/log/journal && sudo systemctl restart systemd-journald`.

**Update**: `sudo /opt/hermes-orchestrator-agent/.venv/bin/pip install --upgrade hermes-orchestrator` then `sudo systemctl restart hermes-orch-agent@*`. (No installer needed for agents — pip + systemctl is the update story.)

**Uninstall**: `sudo systemctl disable --now hermes-orch-agent@*` → `sudo rm -rf /opt/hermes-orchestrator-agent /etc/hermes-orchestrator` → `sudo userdel hermes-agent`.

## 9. Upgrade flow

In-app:
- Dashboard shows "Update available" banner when service hits a manifest URL
- Click → downloads new wheel → stops service → installs wheel in venv → restarts service
- DB migrations run as part of `pip install` post-hooks (or as a separate `hermes-orch migrate` command)
- Migrations are forward-only, versioned in `db.py` (we already have this pattern)

Manual upgrade:
- Run new installer with "upgrade" mode (detect existing service + data dir)
- Installer stops service, copies new files over old, reinstalls deps in venv, runs migrations, starts service

**Zero-downtime upgrade is post-v1.0**. For v1.0 a 5-30s downtime is fine.

---

## 10. Uninstall flow

- "Programs and Features" → Hermes Orchestrator → Uninstall
- Stops service, removes watchdog task, removes service registration, deletes install dir, **asks user** whether to delete data dir (default: keep — projects are valuable)
- Keeps `%APPDATA%\hermes-orchestrator\config.yaml` per user (their LLM key, in case they re-install)

## 11. Security

For semi-tech audience, the user **is** the trust boundary for v1.0. Specifically:

- **HMAC auth** between orchestrator and agent hosts (v1.6+, done)
- **API key** stored in user's config.yaml with ACL: only that user + Administrators can read
- **No inbound ports from internet** (default: bind to 127.0.0.1). For LAN access, the wizard should offer "Allow LAN access" checkbox which binds to 0.0.0.0
- **HTTPS deferred** to post-v1.0 (the user profile says this; productize as part of TLS work)
- **No telemetry** sent anywhere

Future (post-v1.0):
- HTTPS with self-signed cert (or Caddy-style auto-cert)
- Optional cloud relay for off-LAN agent hosts
- SSO (Azure AD / Google Workspace) for the dashboard

## 12. Open questions for v1.0 (defer if no time)

1. **Auto-update** or manual? Spec above assumes manual-via-dashboard. Auto-update is risky for non-tech users (no rollback story).
2. **Multi-orchestrator on one box** (dev + prod) — out of scope, use different ports + dirs manually
3. **Backup** — out of scope, user just copies `C:\ProgramData\hermes-orchestrator\` if paranoid
4. **Restore from backup** — out of scope
5. **Web UI for service management** (start/stop from dashboard) — nice-to-have, defer

## 13. Out of scope (explicit non-goals for v1.0)

- Linux install
- macOS install
- Docker container
- Cloud-hosted version (hosted hermes-orchestrator.com or similar)
- White-label / multi-tenant
- Plugin marketplace
- Per-step user permissions (everyone who can reach the dashboard can do anything)
