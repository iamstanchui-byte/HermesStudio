## 2. Problem statement — `install_command` (P3.3)

### 2.1 What the user saw

The user installed an agent host for the first time, generated
an enrollment token from the dashboard, copied the install
command, and ran it. They got:

```
$ hermes-orch-agent enroll --server http://192.168.2.152:8765 \
    --token etok-... --agent-name win-01
hermes-orch-agent: command not found
```

The CLI was not installed on the host because the `install_command`
returned by the API was only the `enroll` invocation — no
`pip install` step.

### 2.2 Spec contract

> §3.3: "install_command is the one-liner the user pastes on the
> agent host"

> §3.3.1: the token is briefly visible via `ps aux` (an accepted
> v1.0.1 limitation)

The one-liner must work end-to-end on a **fresh** host with
nothing installed. The previous implementation assumed the
host already had `hermes-orch-agent` on PATH.

### 2.3 What changed (P3.3 fix, commit `03fdd33`)

`src/hermes_orch/api/enrollment.py` — `post_enrollment_token`:

**Before** (commit `004f5eb`):
```python
install_command = (
    f"hermes-orch-agent enroll "
    f"--server {server_url} "
    f"--token {issued.plaintext} "
    f"--agent-name {issued.requested_agent_name or 'agent-1'}"
)
```

**After** (commit `03fdd33`):
```python
install_command = (
    f'pip install "hermes-orchestrator @ git+https://github.com/iamstanchui-byte/HermesStudio.git" && '
    f"hermes-orch-agent enroll "
    f"--server {server_url} "
    f"--token {issued.plaintext} "
    f"--agent-name {issued.requested_agent_name or 'agent-1'}"
)
```

The `hermes-orchestrator` Python package (per `pyproject.toml`)
exposes both CLIs:
```toml
[project.scripts]
hermes-orch = "hermes_orch.cli:cli"
hermes-orch-agent = "hermes_orch.agent_cli:cli"
```

One `pip install` → both binaries on PATH.

### 2.4 Polish batch (commit `7dd092c`)

#### 2.4.1 Tag pin `@v0.10.0`

```python
# After (commit 7dd092c)
install_command = (
    f'pip install "hermes-orchestrator @ git+https://github.com/iamstanchui-byte/HermesStudio.git@v0.10.0" && '
    f"hermes-orch-agent enroll "
    f"--server {server_url} "
    f"--token {issued.plaintext} "
    f"--agent-name {issued.requested_agent_name or 'agent-1'}"
)
```

The tag pin matches `pyproject.toml` `version = "0.10.0"`. Without
it, `pip install` from `git+https://...` resolves to whatever
`main` HEAD points at — every fresh install between milestones
picks up unreleased commits. `@v0.10.0` locks the install to the
released artifacts. The tag must be pushed to the remote
(`git push origin v0.10.0`) or the fresh install will fail with
"Could not find a tag or branch 'v0.10.0'".

#### 2.4.2 Prerequisite hint in the enroll modal

`src/hermes_orch/templates/agents.html` — amber box above the
install command block:

> **Prerequisites** on the agent host: `python 3.10+`, `pip`, `git`.
> Linux/Mac: usually pre-installed. Windows: install Python from
> python.org with "Add to PATH" checked, then run
> `pip install git` if git isn't already on PATH.

Rationale: `install_command` runs `pip install git+https://...`
which needs `python 3.10+`, `pip`, AND `git` on the agent host's
PATH. A fresh minimal Linux image or a clean Windows box would
fail with cryptic "git: command not found" and the operator has
no clue what prerequisite is missing. The hint surfaces the
prereq list at the moment of paste, not after a failed run.

### 2.5 Canonical URL rationale (Perplexity P0)

The install URL is
`git+https://github.com/iamstanchui-byte/HermesStudio.git@v0.10.0`
but the package name in `pyproject.toml` is `hermes-orchestrator`.
Perplexity flagged this as a P0 — looks like a typo or a
misdirected install. **The disconnect is intentional and stable**:

- `HermesStudio` is the user's umbrella GitHub repo (a single
  monorepo holding the orchestrator + a few sibling projects).
- `hermes-orchestrator` is the name of THIS project inside that
  monorepo — the package name on the import path; the project
  name in `pyproject.toml`'s `[project] name`; the entry-point
  name `hermes-orch`.

The pip install target is `<package-name> @ <git+url>@<tag>`. What
matters for pip is that the git ref contains a
`hermes-orchestrator/` package matching the `[project] name` in
`pyproject.toml`. The umbrella repo name is just a URL; the
package name is what pip imports.

If this ever needs to change, the change is in `pyproject.toml`
first (so the canonical source of truth updates), then in the
install URL generator. A guard test
(`test_issue_token_install_command_url_is_canonical`) ensures
silent drift fails CI.

### 2.6 Decisions / tradeoffs

- **Why `git+https://...` instead of a published wheel?**
  The package isn't on PyPI. `git+https` is the simplest install
  path that doesn't require a separate publish step. The polish
  batch adds a tag pin (`@v0.10.0`) so the install is locked to
  a known release rather than tracking `main`.

- **Why `pip` and not `pipx` / `python -m pip`?**
  `pip` resolves to whichever Python is active (system or
  venv). `pipx` is the recommended isolated install for a
  long-lived daemon but adds a dependency. The default
  `pip install` works for both a venv-based setup (with venv
  activated) and a system install (acceptable for a personal
  Linux box). The prereq hint in the UI covers the case where
  the user has no `pip` at all.

- **Why `&&` and not `;`?**
  `&&` short-circuits on failure — if `pip install` fails
  (network error, missing venv, missing git), we don't try to
  `enroll` with a non-existent CLI. PowerShell users translate
  to `;`. Known limitation; documented in §8.

## 3. Problem statement — 600ms redirect race (Q2 polish)

### 3.1 What the user saw

After clicking "Use starter" on the onboarding page, the JS
showed "Cloned!" then waited 600ms before redirecting to the
workflow detail page. On slow renders the status text never
appeared; on fast renders the user could blink and miss it.

### 3.2 What we did

`src/hermes_orch/templates/onboarding.html` (commit `7dd092c`):

**Before** (race-prone):
```js
if (r.ok) {
    const data = await r.json();
    if (status) status.textContent = 'Cloned!';
    setTimeout(() => {
        window.location.href = `/workflows/${data.workflow_id}`;
    }, 600);
}
```

**After** (no race):
```js
if (r.ok) {
    const data = await r.json();
    if (status) status.textContent = 'Cloned!';
    // Immediate redirect with the starter name as a query param.
    // The workflow detail page reads `?cloned_from=<name>` and
    // shows a one-time banner: "Cloned from starter: Research brief".
    window.location.href =
        `/workflows/${data.workflow_id}?cloned_from=${encodeURIComponent(name)}`;
}
```

`src/hermes_orch/templates/workflow_detail.html` (commit
`7dd092c`): reads the `?cloned_from=<name>` query param, looks up
the starter catalog for the human title + icon, and shows a
dismissable emerald banner:

> 📦 **Cloned from starter: Research brief**
> (snapshot — updates to the catalog won't auto-migrate this clone)

The banner is per-page-load (no localStorage) — refresh and it
goes away, so the user isn't nagged after they've seen it.

### 3.3 Why not just a longer delay?

A longer `setTimeout` (e.g. 2 seconds) is still a race: the
browser may decide to repaint, may pause for some other reason,
or the user may have already clicked elsewhere. Carrying the
context (`?cloned_from=<name>`) to the destination page is
race-free by construction.

## 7. Live bug fix — ISO 8601 string heartbeats

### 7.1 What broke

During the live E2E walk above, the first call to
`/api/starters/system-health/clone` + dispatch returned a
healthcheck that **crashed** in `_isoformat` /
`_to_unix`:

```
TypeError: float() argument must be a string or a real number, not 'NoneType'
```

### 7.2 Root cause

`core/healthcheck.py` `_isoformat(ts)` and `_to_unix(ts)`
assumed the `agents.last_heartbeat` column was a unix
timestamp int/float. But `db.py` stores it as a SQLite
TIMESTAMP, and aiosqlite surfaces TIMESTAMP columns as ISO 8601
strings (with or without `T` separator, with or without tz
offset, with or without `Z` suffix, or SQLite's
space-separated form `2026-08-08 15:58:02.170373`). On a fresh
install the column is `NULL`; on a healthy install it's ISO;
on a debug install it could be a unix float. The helpers
weren't prepared for any of these.

### 7.3 The fix

`core/healthcheck.py` (commit `7dd092c`):

```python
def _to_unix(ts: float | int | str | None) -> float | None:
    """Coerce a heartbeat timestamp to a unix float, accepting
    unix int/float OR ISO 8601 string OR None/empty/garbage.
    Naive ISO timestamps (no tz) are assumed UTC.
    """
    if ts is None or ts == "":
        return None
    s = str(ts).strip()
    if not s:
        return None
    # Try ISO 8601 first (the aiosqlite default).
    try:
        dt = datetime.fromisoformat(s.replace("Z", "+00:00"))
        if dt.tzinfo is None:
            dt = dt.replace(tzinfo=timezone.utc)
        return dt.timestamp()
    except (ValueError, TypeError):
        pass
    # Fall back to a unix timestamp int/float.
    try:
        return float(s)
    except (ValueError, TypeError):
        return None
```

`_isoformat` got the same treatment. Both are now total
functions over `(float | int | str | None)`.

### 7.4 Regression tests (2 new)

`tests/test_healthcheck.py`:

```python
async def test_healthcheck_handles_iso_string_heartbeats(fresh_db):
    """Regression: ISO 8601 heartbeats don't crash the helpers."""
    now = datetime.now(timezone.utc)
    # aiosqlite's TIMESTAMP format
    iso_utc = now.isoformat()
    iso_local = now.astimezone().isoformat()
    iso_z = now.isoformat().replace("+00:00", "Z")
    iso_no_t = now.strftime("%Y-%m-%d %H:%M:%S.%f")
    for iso in (iso_utc, iso_local, iso_z, iso_no_t):
        assert _to_unix(iso) is not None
        assert _isoformat(iso) is not None

async def test_healthcheck_handles_null_and_empty_heartbeats(fresh_db):
    """Regression: None / empty / '0' heartbeats don't crash."""
    for nullish in (None, "", "0", "garbage"):
        assert _to_unix(nullish) is None
        assert _isoformat(nullish) is None
```

The live walk now completes end-to-end without crash.

## 8. Decisions log (full v1.0.1 milestone)

The full milestone is 17 commits across 4 phases + 3 follow-up
fix batches. Key design decisions (preserve in future iterations):

### P0: Default bind host
- `bind_host: 127.0.0.1` (loopback only) as the secure default;
  legacy `host:` config auto-migrates with one-time log

### P1: Bind toggle + restart endpoint
- LAN toggle is a config + restart, **never** an in-place
  rebind (a live socket listener cannot rebind without restart)
- 3 restart strategies: supervised (env var explicit), direct
  (Python + .py argv), undetectable (frozen / embedded)
- `wmic` was removed in Windows 11 24H2 → switched to
  PowerShell `Get-CimInstance` (P1.3, commit `bac8b27`)
  - **Edge case to watch**: PowerShell with restricted
    execution policy (GPO-locked environments) may block
    `Get-CimInstance`. Documented as a known risk; not blocking
    ship.
- The worker's immediate parent is `python.exe` (uvicorn
  master), not `hermes-orch.exe`; walked up the ancestor
  chain to find the launcher (P1.2, commit `054c2b9`)

### P2: Onboarding state
- 4 success signals + 1 informational
  (`first_task_attempted` is **not** in the collapse set)
- `users.onboarding_state` JSON column; backfill for existing
  users on upgrade (never reset in-progress)
- Single-tenant assumption: task events flip signals for
  all users (typical one-admin setup)
  - **Technical debt for v1.1**: per-user task ownership
    tracking is needed when the product goes multi-user.
- `first_task_completed` is **only** true on `status=completed`
  (per spec T1.11)

### P3: Enrollment tokens
- 256-bit token (32 bytes via `secrets.token_urlsafe(32)`)
- SHA-256 hash stored, plaintext never persisted
- 15-min expiry, single-use
- Atomic consume via `UPDATE ... WHERE used_at IS NULL AND
  expires_at > now` in a single transaction
- Agent-declared `agent_name` **always** wins over the
  operator's `requested_agent_name` hint (per spec §3.3.2)
- `used_by_agent_id` written back in the same transaction
- Known limitation: token briefly visible via `ps aux` during
  install (accepted for v1.0.1; deferred to v1.1: stdin-based
  delivery)
- Polish (`7dd092c`): install URL is tag-pinned `@v0.10.0`,
  UI shows prerequisite hint, canonical URL has a guard test

### P4: Starter catalog + healthcheck
- Bundled read-only YAMLs at `src/hermes_orch/starters/*.yaml`
  (4 starters: research-brief, system-health, backtest-stater,
  daily-monitor)
- Clone-on-demand → user-owned `workflow_packages` row (no
  auto-seed; the user can clone the same starter multiple
  times)
- `_server_healthcheck` is a **server-side magic action** that
  the supervisor recognizes in `_assign_task` and runs
  in-process (no agent dispatch, no LLM call). Per §3.5.1:
  - 0 agents → status=failed (flips `first_task_attempted`
    only, NOT `first_task_completed`)

## 12. Known limitations (deferred to v1.1+)

These are explicit deferred items from the spec, not bugs:

1. **Token visible via `ps aux` during install** (§3.3.1) — the
   one-liner puts the token in argv; any other local process
   can read it via `ps aux` during the brief execution window.
   15-min expiry + single-use limits blast radius. v1.1:
   stdin-based or short-lived-URL-based delivery.

2. **"Update to latest" button on workflow detail** — the
   starter catalog is a snapshot; updates to bundled YAMLs
   don't auto-migrate user clones. v1.1: per-clone version
   tracking + one-click update.

3. **PowerShell `&&` in install_command** — PowerShell uses
   `;` for command chaining. The default one-liner uses
   `&&` (bash/zsh convention). PowerShell users translate.
   v1.1: detect shell and emit the right separator.

4. **Restart does not drain in-flight tasks** (§3.7) —
   triggering a server restart does not gracefully wait for
   in-flight tasks. Tasks in `running` status at restart
   time may stay `running` in the DB until the agent's
   next heartbeat corrects them. Accepted for v1.0.1.

5. **Single-tenant onboarding assumption** — task events flip
   onboarding signals for all users, not just the task
   owner. Fine for the typical one-admin setup but needs
   per-user task ownership tracking in v1.1 if the product
   goes multi-user.

6. **`Get-CimInstance` blocked by restricted PowerShell
   execution policy** — in GPO-locked environments the
   ancestor-chain launcher detection (P1.2) may not work.
   Edge case; not blocking ship. v1.1: provide a
   `.cmd`-based fallback that doesn't depend on PowerShell
   cmdlets.

## 13. Follow-up tickets (post-v1.0.1)

### 13.1 v1.1.1 — Pre-existing 209 test failures cleanup

**Decision (2026-08-09, Perplexity review)**: do **NOT** add a
hardcoded 209-name baseline list to the v1.0.1 milestone. A
known-failure list becomes a permanent trash can — old failures
are never investigated, just suppressed.

Instead, use **strict xfail + issue ID by root cause**:

- Each pre-existing failure gets a one-line `@pytest.mark.xfail(
  reason="ISSUE-XXXX: <root cause>", strict=True)` annotation
  in the test file. The `strict=True` makes the test FAIL
  (not just XFAIL) if it suddenly passes — that's the signal
  to remove the annotation and close the issue.
- Issues are filed by **root cause**, not by test name. A
  single root cause (e.g. "tests predate dashboard auth → 401")
  may cover 50+ tests; one issue + one PR fixes them all.
- The baseline count is a moving target managed via the issue
  tracker, not a hardcoded list. When the count drops, the
  issue list shrinks; it never silently grows.

**Why this approach over a hardcoded list**:
- A hardcoded list is a maintenance debt from day one — every
  test rename, every test split, every test merge requires
  updating the list.
- Strict xfail + issue ID is test-local — the annotation lives
  next to the test it covers. Renaming a test renames its
  annotation in the same diff.
- The `strict=True` mode forces the failure to be addressed:
  an xfail that starts passing is a real signal, not a
  quiet improvement.

**Ticket body draft** (to be filed as part of v1.1.1 work):
1. Inventory the 209 pre-existing failures, group by root
   cause (auth, cookie middleware, sidebar dep, ...). Expect
   ~5-10 distinct root causes.
2. File one issue per root cause with a representative test +
   count of similar tests.
3. Add `@pytest.mark.xfail(reason="ISSUE-XXXX: ...", strict=True)`
   to each affected test, one PR per root cause.
4. Triage weekly: any xfail that starts passing → close the
   issue → remove the annotation in the same PR.
5. Target: reduce to 0 xfails by end of v1.1 cycle. The
   `strict=True` mode ensures the only way out is real fixes.
