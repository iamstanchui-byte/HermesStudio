## 1. Background

Hermes workflow 已支援 multi-step DAG + multi-agent dispatch（v3.12.6 incremental editing + v3.12.7 wrapper env fix + v3.12.8 token usage）。Workflow 由 `step_template`（JSON list）描述，每 step 透過 `run_workflow` API（`api/workflows.py:1373`）展開成 `tasks` table 嘅 rows，supervisor tick 自動 dispatch `action: "do_task"` 嘅 row 去合適嘅 agent profile。

**Gap**：runtime workflow 暫時係「agent 一條龍跑完」，冇 human gate。對高風險步驟（發外部 email、改 production config、做交易）冇辦法強制 user 睇一眼先繼續。舊嘅 `docs/approval-design.md` (Sprint B draft) 想過加 magic-link email approval path，但從未 ship，scope 太複雜（external user、email infra、token-based auth）。

## 2. Problem

Use cases 一定要 human gate：

1. **發外部 email / 報告前** — agent 寫完草稿，user 睇咗先 send
2. **做交易 / 改 production config 前** — agent propose 改動，user approve 先 apply
3. **根據分析結果揀邊條分支** — 兩條 route 都有 value，由 user 揀
4. **審批步驟多於一個** — 同一 workflow 可能要 user 喺多個 step 簽名（e.g. legal + finance）

現有 escape hatch 全部要 agent 自己問（透過 chat），冇 systematic 強制 gate：

- 個 agent 可以問 user（design-time），但 user 唔答 agent 都會繼續行落去
- chatbox 有 diff preview + user confirm，但係 design-time 唔係 runtime step gate
- 冇 audit trail 記低「邊個 step 點解要人批」

對半技術 user（product target audience），需要：
- 喺 workflow 定義階段明講「呢步要人批」
- 個 step 跑到時自動停喺 pending state，唔 dispatch agent
- 喺 dashboard inbox 見到 + 點擊就 approve / reject
- audit log 記低邊個 step 邊個 user 點決定
- 冇 timeout 時可以等到天荒地老；要有 TTL 防 zombie

## 3. Goals / Non-goals

### Goals

- 喺 workflow schema 加新 step type `human_approval`，明確表達「呢步要人批，唔 dispatch agent task」。
- 跑到 `human_approval` step：
  - 創建 `ApprovalRequest` row（status = `pending`）。
  - 個 step 保持 `pending` execution state，supervisor 唔 dispatch agent。
  - 個 ApprovalRequest 出現喺 dashboard inbox，user 可以 Approve / Reject。
- Approve → 視 step 為 `completed`，depend on 呢個 step 嘅子節點可以 ready。
- Reject → 根據 `on_reject` 決定 step 終 state，控制 workflow 行為（stop / skip / route）。
- Timeout sweeper（on supervisor tick）處理 zombie approvals。
- Workflow cancel 自動 reject pending approvals，避免 inbox 留 zombie。

### Non-goals (v1)

- **不做 multi-user / role-based approval**：owner 就係 single user。Audit log `user_id` 留 field 為將來。
- **不做 policy engine**（e.g. amount > X 要二人批准）。
- **不在 v1 完整實作 notification system**：先留 generic webhook / event hooks，將來接 Slack / email。
- **不改 supervisor / task dispatcher core semantics**：只係加多一種 task action (`human_approval`) + 狀態 gate。
- **Reject 為不可逆操作**：v1 不提供「un-reject」。如需重試，需開新 workflow run。
- **不做 magic-link / external user approval**（舊 `approval-design.md` 嘅 path）：v1 純 dashboard，唔搞 email infra。

## 4. Proposed solution

### 4.1 Workflow step type: `human_approval`

在 workflow `step_template` 加新 step：

```json
{
  "name": "approve-send-report",
  "type": "human_approval",
  "depends_on": ["generate-report"],
  "approval": {
    "on_reject": "stop",
    "route_to": "manual-review",
    "summary_template": "Approve sending report to {{generate-report.client_name}} with total = {{generate-report.total}}.",
    "timeout_seconds": 86400
  }
}
```

`approval` object fields：

| Field | Required | Default | Notes |
|---|---|---|---|
| `on_reject` | yes | — | `"stop"` / `"skip"` / `"route"` |
| `route_to` | iff `on_reject = "route"` | — | 必須係 workflow 內另一個 step 名；D.depends_on 必須包含此 step（§4.5） |
| `summary_template` | yes | — | Custom regex 模板，syntax `{{var}}` / `{{step_name.field}}`（§4.7） |
| `timeout_seconds` | no | 86400 (24h) | TTL；超時視為 `expired`（走 `on_reject` 同一條路） |

> **Note on `type` vs `action` mapping**: workflow step 用 `type` field（per spec convention），`api/workflows.py:run_workflow` 喺寫入 `tasks` table 時會將 step `type` map 到 task `action` column。即：
> - step `type: "do_task"` → task `action = "do_task"`
> - step `type: "human_approval"` → task `action = "human_approval"`
>
> Supervisor dispatch logic 根據 task `action` 決定行為（§4.4）。`action` 命名沿用而家 `tasks.action` column 嘅 convention。

### 4.2 DB schema: `approval_requests` table

新 table（additive migration，唔影響現有 schema）：

```sql
CREATE TABLE IF NOT EXISTS approval_requests (
    id              TEXT PRIMARY KEY,           -- "apr-{short_id}"
    workflow_id     TEXT NOT NULL,              -- projects.id（project 即係一個 workflow run）
    step_name       TEXT NOT NULL,              -- 對應 step_template 入面嘅 step name
    status          TEXT NOT NULL DEFAULT 'pending',  -- pending | approved | rejected | expired
    summary         TEXT NOT NULL,              -- render 後嘅 summary string
    payload         TEXT,                       -- serialized string（JSON-stringified or plain text）
    created_at      TEXT NOT NULL,              -- ISO 8601
    decided_at      TEXT,                       -- ISO 8601，null until acted on
    reason          TEXT,                       -- reject / expired / cancelled 嘅 optional message
    user_id         TEXT,                       -- audit：邊個 user 決定
    FOREIGN KEY (workflow_id) REFERENCES projects(id) ON DELETE CASCADE
);

CREATE INDEX IF NOT EXISTS idx_approval_workflow  ON approval_requests(workflow_id);
CREATE INDEX IF NOT EXISTS idx_approval_status    ON approval_requests(status);
CREATE INDEX IF NOT EXISTS idx_approval_created   ON approval_requests(created_at);  -- sweeper 用
```

`payload` field：

- 係 **TEXT serialized string**（非 structured object）。
- 內容可以係 JSON-stringified object（structured diff）或 plain text（email body）。
- 15MB cap（§4.9）作用喺 serialized string length。

`status` state machine：

```
pending ──[user approve]──> approved
        ──[user reject]──> rejected
        ──[timeout]────> expired
        ──[workflow cancel]──> rejected  (reason="workflow_cancelled")
```

### 4.3 Execution state vs Approval state

兩個獨立 state machine，互相用 FK 連：

**`tasks.action = "human_approval"` 嘅 step**：
- 個 task 仍係 `tasks` table row，`tasks.status` 用 execution state：
  - `pending` → `running` → `completed` / `failed` / `skipped`
- Supervisor 唔 dispatch `human_approval` action（§4.4），所以 `running` state 唔會出現。
- Approve / Reject 決定最終 `tasks.status`：
  - Approve → `completed`（`completion_reason = "approved_by_human"`）
  - Reject + `on_reject = "stop"` → `failed`（`failure_reason = "rejected_by_human"`）
  - Reject + `on_reject = "skip"` → `skipped`
  - Reject + `on_reject = "route"` → `skipped`（由 D.depends_on route semantics 推 D ready，§4.5）
- Expired → 視為 rejected，套用 `on_reject` semantics

**`approval_requests.status`**：獨立 approval state machine（§4.2）。

**依賴 gate**（downstream 步驟 readiness）：

- Dependents 只睇 `tasks.status in {"completed", "skipped"}`，**唔直接睇 `approval_requests.status`**。
- 呢個 decoupling 嘅好處：supervisor 唔需要 join approval table 嚟做 DAG scheduling；approval state 完全 orthogonal to execution state。

### 4.4 Supervisor dispatch gate

Supervisor tick loop（`api/core/supervisor.py`）每 N 秒行一次。當前 dispatch 規則：

```python
# 簡化 pseudo-code
for task in pending_tasks:
    if task.action == "do_task":
        # 既有邏輯：capability check → SOUL preset → agent profile 配對 → dispatch
        ...
    elif task.action == "human_approval":
        # 新 gate：唔 dispatch agent task，改為創建 ApprovalRequest
        if all_deps_completed_or_skipped(task):
            if not exists_pending_approval(workflow_id, step_name):
                summary = render_summary(step.approval.summary_template, context)
                create_approval_request(workflow_id, step_name, summary, payload)
                emit_event("approval.created", payload)
        # 唔再做任何嘢，等 user 決定
```

`all_deps_completed_or_skipped(task)`：

```python
def all_deps_completed_or_skipped(task):
    if not task.depends_on:
        return True
    for dep_tid in task.depends_on:
        dep = get_task(dep_tid)
        if dep.status not in ("completed", "skipped"):
            return False
    return True
```

注意：`failed` / `rejected` (冇 skip) 都 block downstream。即 `on_reject = "stop"` 嘅 rejection 會 freeze 整個 workflow。

### 4.5 `on_reject: "route"` semantics

對 `on_reject = "route"` 嘅 step B：

- Reject 時：
  - `approval_requests.status = "rejected"`（reason 由 user 填）
  - `tasks[B].status = "skipped"`（表示此 step 冇執行 agent task）
- Route target step D：
  - 必須存在於 workflow 內
  - **必須喺 D.depends_on 列出 B**（explicit DAG edge）— runtime 唔自動 inject dependency
  - User 寫 workflow 時要自己 ensure `D.depends_on.contains(B)`
- 其他 depend on B 嘅 step E：
  - 見到 `tasks[B].status = "skipped"` → 在 E 其他 deps 滿足時亦可 ready
  - `skipped` 視為 success-equivalent（propagates as completed）
  - 即：E 唔需要做任何 special handling

**Create-time validation**（workflow save 時做）：

```python
def validate_workflow(steps):
    for step in steps:
        if step.get("type") == "human_approval":
            approval = step.get("approval", {})
            if approval.get("on_reject") == "route":
                target = approval.get("route_to")
                if not target:
                    raise ValidationError("route requires route_to")
                target_step = find_step_by_name(steps, target)
                if not target_step:
                    raise ValidationError(f"route_to={target} not found")
                if step["name"] not in target_step.get("depends_on", []):
                    raise ValidationError(
                        f"route_to={target} must list {step['name']} in its depends_on"
                    )
            # summary_template validation (§4.7)
            validate_summary_template(...)
```

Validation failure → workflow save 返 `422 Unprocessable Entity`，response body 列明邊個 step / 邊個 variable 唔 valid。

### 4.6 Approve / Reject API

三個新 endpoint：

```
POST /api/workflows/{workflow_id}/steps/{step_name}/approve
POST /api/workflows/{workflow_id}/steps/{step_name}/reject
GET  /api/workflows/{workflow_id}/approvals          # 列出 workflow 嘅 approval history
```

**Approve behavior**：

```
1. SELECT approval_request WHERE workflow_id=? AND step_name=? AND status='pending'
2. If not found:
   - 如果有 approval row 但 status != 'pending':
     - If 'approved': 200 OK + current state (idempotent)
     - If 'rejected' or 'expired': 409 Conflict
   - 如果完全冇 row: 404
3. If 'pending':
   a. UPDATE approval_requests SET status='approved', decided_at=now, user_id=current_user
   b. UPDATE tasks SET status='completed', completion_reason='approved_by_human'
   c. emit_event('approval.approved', {workflow_id, step_name, user_id})
   d. audit_log('approval.approved', ...)
4. Return 200 OK + { approval_id, status, decided_at }
```

**Reject behavior**：

```
1. SELECT approval_request (same as Approve)
2. If 'pending':
   a. body = { reason?: str }  (optional user message)
   b. UPDATE approval_requests SET status='rejected', decided_at=now, user_id=current_user, reason=body.reason
   c. 根據 on_reject:
      - 'stop'  → UPDATE tasks SET status='failed', failure_reason='rejected_by_human'
                  + 標記 project.state = 'failed'（graceful stop, §4.6.3）
      - 'skip'  → UPDATE tasks SET status='skipped'
      - 'route' → UPDATE tasks SET status='skipped' (D 喺 D.depends_on 滿足時 ready，§4.5)
   d. emit_event('approval.rejected', {workflow_id, step_name, user_id, reason, on_reject})
   e. audit_log('approval.rejected', ...)
3. If already 'rejected' or 'expired' or 'approved': 409 Conflict
4. Return 200 OK
```

**Idempotency**：
- Approve 兩次 → 第二次 200 + current state，唔再 schedule downstream 第二次
- Approve after expired → 409（已過期限）
- Reject after approved → 409（user 已 approve，唔可以再 reject）
- Race: timeout sweeper + user click Approve 同一瞬間 → atomic UPDATE with `WHERE status='pending'`，得一個 winner

**Auth**：
- v1 single-user：現有 dashboard session cookie (v3.4 auth) 已經足夠
- `user_id` 從 session 攞
- 將來 multi-user 時：可以加 `POST /api/approvals/by-token/{token}/respond` magic-link path（deferred, see Future work）

#### 4.6.1 Timeout sweeper (on supervisor tick)

唔引入新 cron / background worker。Supervisor tick 既有的 DB query loop 加多一段：

```python
# 在 supervisor tick 中，每 N ticks (e.g. 每 30s) 跑一次
def sweep_expired_approvals():
    now = datetime.utcnow()
    pending = db.query("""
        SELECT * FROM approval_requests
        WHERE status = 'pending'
          AND datetime(created_at, '+' || timeout_seconds || ' seconds') < ?
    """, (now,))
    for apr in pending:
        # 原子 update：避免重複 sweeper race
        affected = db.execute("""
            UPDATE approval_requests
            SET status='expired', decided_at=?, reason='timeout', user_id='system'
            WHERE id=? AND status='pending'
        """, (now, apr.id))
        if affected == 0:
            continue  # user 喺同一瞬間 approve / reject 咗
        # Apply on_reject semantics
        apply_on_reject(workflow_id=apr.workflow_id, step_name=apr.step_name, on_reject=...)
        emit_event('approval.expired', {...})
        audit_log('approval.expired', ...)
```

> **Note**: Sweeper 頻率建議 ≥ 30s（避免太密 hit DB），但 spec 唔強制。實作時可放 supervisor tick 內 + 個 counter，每 6 ticks (~30s on 5s tick) 跑一次。

#### 4.6.2 Workflow delete (cascade)

Deleting a workflow（`DELETE /api/projects/{id}` 既有機制）：

- `approval_requests` 嘅 `FOREIGN KEY (workflow_id) REFERENCES projects(id) ON DELETE CASCADE` 自動 cascade delete
- 冇 orphan approval records
- v1 唔做 soft-delete（將來 audit 需要再考慮，見 Future work）

#### 4.6.3 Workflow cancel (graceful stop)

Cancel workflow（`POST /api/projects/{id}/cancel` 既有機制）：

1. `projects.state = "stopping"`（新 transient state，唔係 terminal）
2. Supervisor 唔再 dispatch 新 task（不論 `action = "do_task"` 或 `"human_approval"`）
3. 所有 pending ApprovalRequests auto-reject：
   ```python
   for apr in db.query("SELECT * FROM approval_requests WHERE workflow_id=? AND status='pending'", (pid,)):
       db.execute("""
           UPDATE approval_requests
           SET status='rejected', decided_at=now, reason='workflow_cancelled', user_id='system'
           WHERE id=? AND status='pending'
       """)
       # 對應 human_approval task 標記 skipped
       apply_on_reject(apr, on_reject='skip')  # 唔再 kill workflow（已經喺 stopping）
       emit_event('approval.rejected', {reason='workflow_cancelled', ...})
   ```
4. In-flight `do_task` 步驟：
   - 允許跑完；result 仍寫入 `tasks.output`
   - **但 downstream steps 唔再 schedule**（supervisor check `project.state == "stopping"` → skip dispatch）
5. Trigger 條件：supervisor 發現 `project.state == "stopping"` AND 冇任何 in-flight task（`status = "running"`）→ set `projects.state = "cancelled"` (terminal)

> **v1 trade-off**: cancel 唔硬 abort running task（agent 仲跑緊可能做緊外部 side effects，例如 send email 寫緊 DB）。Graceful stop 確保 cancel 後冇新 work，但允許 in-flight 完成。User cancel = terminal，唔可以 resume（要新 workflow run）。

### 4.7 `summary_template` data flow + validation

#### 4.7.1 Render context

`summary_template` 喺 ApprovalRequest 創建時 render 一次（`created_at` 嗰刻），result 存 `approval_requests.summary` column。Render context：

```python
context = {
    # 1. 本 step 嘅 params
    **step.params,  # 從 step_template.params_template + run_workflow 嘅 variables
    # 2. Upstream step outputs (dotted path)
    # e.g. {{generate-report.client_name}} → tasks[generate-report].output["client_name"]
    **flatten_upstream_outputs(dep_tasks),
}
```

`flatten_upstream_outputs` 將每個 dep task 嘅 `output` JSON 攤平做 `step_name.field.subfield` 形式。例如：

```python
# task "generate-report".output = {"client_name": "ACME", "total": 1.2M, "breakdown": {...}}
context["generate-report.client_name"] = "ACME"
context["generate-report.total"] = 1.2M
context["generate-report.breakdown"] = {...}
```

Dotted path 支援 nested access：

```python
# {{generate-report.breakdown.by_category}} 
# → context["generate-report"]["breakdown"]["by_category"]
```

#### 4.7.2 Templating engine

**Custom regex-based template**（唔用 Jinja2，避免 code execution risk）：

```python
import re

_VAR_RE = re.compile(r"\{\{(\w+(?:\.\w+)*)\}\}")

def render_summary(template: str, context: dict) -> str:
    """Render {{var}} or {{step_name.field}} against context.

    Missing keys render as literal `<missing:key>` placeholder so the
    user can spot typos immediately (vs rendering empty string which
    hides the problem).
    """
    def replace(m):
        key = m.group(1)
        if "." in key:
            # dotted path: walk the nested dict
            parts = key.split(".")
            cur = context
            for p in parts:
                if not isinstance(cur, dict) or p not in cur:
                    return f"<missing:{key}>"
                cur = cur[p]
            return str(cur)
        return str(context.get(key, f"<missing:{key}>"))
    return _VAR_RE.sub(replace, template)
```

**Syntax**：

- `{{var}}` — 單一 identifier
- `{{step_name.field}}` — dotted path，支援 nested
- 其他 template 行為（filter、loop、expression）— **唔支援**

#### 4.7.3 Create-time validation (REQUIRED)

> 成本低（約 20 LOC：regex parse + set membership check）。
> 避免 runtime surprise（missing variable 導致 summary 顯示 `<missing:...>` literal placeholder）。

```python
def validate_summary_template(template: str, params_keys: set, dep_step_names: set) -> list[str]:
    """Return list of validation errors (empty if OK)."""
    errors = []
    for var_match in _VAR_RE.finditer(template):
        key = var_match.group(1)
        if "." in key:
            step_name = key.split(".")[0]
            if step_name not in dep_step_names:
                errors.append(f"{{{{{key}}}}} references step '{step_name}' which is not in depends_on")
        else:
            if key not in params_keys:
                errors.append(f"{{{{{key}}}}} not in params_template keys: {sorted(params_keys)}")
    return errors
```

**Validation scope note**：

- ✅ 驗證 `{{step_name.field}}` 嘅 `step_name` 部分係真嘅 upstream dependency
- ❌ **唔驗證** `field` 部分是否存在於 upstream step 嘅 output schema（output 係 runtime 由 agent 產生，schema 唔 static）
- 若 runtime 渲染時 `field` missing：renderer 輸出 `<missing:step_name.field>` literal placeholder，user 喺 approval summary 見到，re-open workflow 修改 template

### 4.8 Webhook / event hooks

每個 `ApprovalRequest` state transition emit 一個 generic event：

| Event | 觸發時機 | Payload 必含 fields |
|---|---|---|
| `approval.created` | Supervisor 創建 ApprovalRequest | `workflow_id, step_name, approval_id, status='pending', summary, created_at, payload_size_bytes` |
| `approval.approved` | User Approve | + `decided_at, user_id, completion_reason='approved_by_human'` |
| `approval.rejected` | User Reject OR Workflow cancel | + `decided_at, user_id, reason, on_reject` |
| `approval.expired` | Sweeper timeout | + `decided_at, user_id='system', reason='timeout', on_reject` |

Emit 介面：

```python
def emit_event(event: str, payload: dict) -> None:
    """v1: 寫 audit log + push 到 internal queue (Slack/email integration 之後 subscribe)."""
    audit_log(actor="approval-system", event=event, payload=payload)
    # 將來: redis.publish("approval.events", json.dumps(payload))
```

v1 implementation 簡單：寫入 audit log table（re-use 而家 `audit_log` infra）+ 可選 push 到 in-memory queue。Slack / email integration 將來 subscribe event bus 就得，唔需要逐個 handler 加 webhook code。

### 4.9 Payload size cap

`approval_requests.payload` serialized string 長度 cap：

- 跟現有 orchestrator task output cap（**15MB**）：
  - 若 `len(serialized) > 15MB`：scheduler 唔創建 ApprovalRequest，返 `413 Payload Too Large` error，task 保持 `pending`（supervisor 會 retry）— 唔好，因為會 infinite retry
  - 改為：scheduler 創建 ApprovalRequest 但 `payload` 設為 `"<truncated: see source>"`，audit log 記錄 truncation event
  - 或者：fallback 寫 `payload` 至 filesystem（`~/.hermes-orchestrator/projects/{id}/approvals/{apr_id}.payload`），DB 只存 path reference
- v1 簡單策略：**reject 個 step，mark task failed with reason="payload too large (>15MB)"，user 收到 task failed notification**。呢個 fail-loud 行為比 silent truncation 安全，user 即刻知有問題。

```python
def create_approval_request(workflow_id, step_name, summary, payload, timeout_seconds):
    if len(payload) > PAYLOAD_CAP_BYTES:  # 15MB
        # fail the task loud
        update_task_status(task_id, "failed", failure_reason=f"approval payload > 15MB cap (got {len(payload)} bytes)")
        emit_event("approval.payload_too_large", {"workflow_id": ..., "step_name": ..., "size": len(payload)})
        return
    db.insert("approval_requests", {...})
```

## 5. UX / Dashboard

### 5.1 Inbox pattern (top-nav badge)

Primary UX：**top-nav inbox icon + badge count**，跨 page 都見到（似 GitHub / email notification）。

  - Workflow 名 / ID

  - Summary（render 後 string）

- 點擊 row → 詳細 view：
  - 完整 payload（email 草稿 / diff / plain text）
  - Approve / Reject 按鈕（Reject 可填 reason）
  - 對 `on_reject = "route"` 嘅 step：詳細 view 同時顯示 route target（"Rejecting will route the workflow to step `manual-review` instead"）

### 5.2 Refresh strategy

- Badge count：`GET /api/inbox/approvals?status=pending` 每 30s polling
- 詳細 view：進入時 fetch `GET /api/inbox/approvals/{approval_id}`，optional 每 10s re-fetch（避免 stale state）
- Approve / Reject 成功後：client-side optimistic update + 5s 之內下次 poll 確認

### 5.3 Reject confirmation dialog (UX safety)

Reject 按鈕 **SHOULD** 顯示確認對話框，尤其對 `on_reject = "stop"` 嘅步驟：

- 對話框展示後果：
  - `on_reject = "stop"`：顯示 "Rejecting will stop the entire workflow"
  - `on_reject = "skip"`：顯示 "Rejecting will mark this step as skipped, downstream steps will continue"
  - `on_reject = "route"`：顯示 "Rejecting will route the workflow to step `<route_to>` instead"
- 對 `stop` 嘅 case，要求 user 明確確認（第二次 click）先 call Reject API
- 對 `skip` / `route` 嘅 case，可以用較輕量嘅確認（一個 inline confirm button），但 v1 建議**所有 Reject 操作至少有一層確認**，避免誤按

```javascript
// Example: Reject button click handler
async function onRejectClick(workflowId, stepName, onReject, routeTo) {
    let confirmMessage;
    if (onReject === 'stop') {
        confirmMessage = "Rejecting will STOP the entire workflow. Continue?";
    } else if (onReject === 'skip') {
        confirmMessage = "Rejecting will mark this step as SKIPPED. Downstream steps will still run. Continue?";
    } else if (onReject === 'route') {
        confirmMessage = `Rejecting will ROUTE the workflow to step "${routeTo}" instead. Continue?`;
    }
    if (!confirm(confirmMessage)) return;
    await postReject(workflowId, stepName, { reason: prompt("Optional reason:") });
}
```
