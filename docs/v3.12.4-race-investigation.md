# Race Investigation: "Profile 'win-agent01' does not exist" (v3.12.4)

**Status:** Investigation paused — root cause still gap, mitigation in place
**Related commits:** `289db74` (race-diag instrumentation, kept on for now)
**Author:** Stanley (via investigation with Minimax)
**Date:** 2026-08-05

---

## 1. Symptom

When dispatching single-tasks to `win-agent01` with
`max_concurrent_tasks = 2`, roughly **70% of tasks fail** with
`tasks.error = "Error: Profile 'win-agent01' does not exist. Create it
with: hermes profile create win-agent01"` (hermes CLI exit code 1).
With `max_concurrent_tasks = 1`, fail rate drops to 0%.

Pair correlation:
- 2 hermes subprocesses starting at the **same microsecond** → 100% both fail
- 40ms apart → mixed
- 50ms+ apart → usually both pass

Failed tasks run hermes for ~10.7-10.9s before exit-1 (hermes CLI entry failure
plus a brief wait-for-input prompt), versus 19-29s for successful tasks.

## 2. What was confirmed

| Hypothesis | Verdict | Evidence |
|---|---|---|
| Two wrappers fighting | ❌ Excluded | PID 13296 + 420 (uv chain) = single instance. No orphan wrapper. `MultipleInstancesPolicy` empty (= `IgnoreNew` default — already correct). |
| Config-write race (`os.replace`) | ❌ Excluded | 5 PASS pairs (10 tasks) all had `os.replace DONE` at the exact same microsecond (0ms apart) with `rc=True` — the atomic write is not the cause. |
| Wrapper stdout block-buffered | ❌ Excluded | Failed tasks had **0 race-diag lines** in `wrapper.out.log`, not just delayed ones. They exited before the very first `click.echo`. |
| Single wrapper, server-side race | ⚠️ Possible | Single wrapper confirmed, race still reproduces 70%. But the actual hermes spawn location is still a gap — see §3. |

`v3.12.4 #4` (`289db74`) added 5 race-diag log sites in `src/hermes_orch/agent_cli.py`
(start of `_apply_hermes_compaction_config`, end of same, internal `os.replace`
done, `Popen` done, hermes `EXIT`). **47 race-diag lines** captured across
8 PASS pairs and 0 fail-task lines. **Keep this instrumentation on** for any
future investigation — it's the only way to disambiguate which code path
actually spawned the hermes that wrote the 96-byte stderr log.

## 3. What's still a gap

The contradiction that we couldn't close:

1. **Hermes really ran.** All 7 failed tasks have `hermes.t-<tid>.stderr.log`
   (96 bytes, "Profile 'win-agent01' does not exist. Create it with...").
   File mtime is `started_at + 8.8s` — hermes was alive and exited ~9s
   after the task started.
2. **Wrapper `_run_task` was NOT called.** `wrapper.out.log` shows
   `[daemon] claim <tid> failed: 400 {"detail":"Task not in assigned
   state: running"}` for every fail task. The wrapper's `_process_one`
   function (`agent_cli.py:3854-3861`) returns immediately on
   `_claim` failure — `_run_task` is never called, so race-diag (1)
   and (4) cannot fire.
3. **Server has no hermes spawn.** Grepped all of `src/` for
   `subprocess.run`, `subprocess.Popen`, `asyncio.create_subprocess_*`,
   `os.system`, `os.popen`, `shell=True`, `runpy`, `importlib`,
   `exec(`, `hermes_bin`, `hermes_cli.main`, `from hermes_cli`,
   `import hermes_cli`. Only `agent_paths.py:38-47` matches — and that
   just queries `hermes config profiles_dir`, not set_active_profile.

So the hermes stderr log is real but its spawn location is unaccounted
for. Possibilities (none yet confirmed):

- A dynamic `exec` path in supervisor that grep didn't catch
  (e.g. `BackgroundTasks`, `asyncio.create_task` callback, or
  `_claim_one` style poll loop running a hermes subprocess that we
  haven't traced to its caller)
- The wrapper has a second `_run_task` call site we haven't found
- A `state.db` SQLite WAL race that bypasses wrapper entirely and
  causes hermes itself to refuse to recognize the profile mid-init
- Stale `hermes.t-<tid>.stderr.log` content from an earlier session
  (rejected — 96 bytes exactly matches the active fail message, and
  mtime is `started_at + 8.8s`)

The most plausible remaining root cause is **(a) supervisor-side hermes
state.db contention** — but we couldn't locate the exact spawn call,
so the story remains an inference rather than a fact.

## 4. Mitigation (in place)

`max_concurrent_tasks = 1` on `win-local-1` → 0% fail rate. Verified across
multiple fresh test batches. This is the production setting until proper
fix is in.

Trade-off: throughput drops to 1× (vs the 4× target). For the user's
heavy backtest/research workflows this is a meaningful regression; for
chat-driven monitoring it's invisible.

## 5. Rejected fix options (premature)

These were considered but **NOT shipped**, per the discipline of "no fix
without confirmed root cause":

- **Option 1: wrapper claim retry** (catch 400, retry 200ms × 2)
  Assumes wrapper claim race is the trigger. But the hermes stderr log
  shows hermes was already running and exited — wrapper claim is a
  symptom, not a cause. Shipping this would mask the real race.

- **Option 2: per-profile hermes serialization on the server**
  Need to know where the server spawns hermes first. Grep returned
  zero hits outside `agent_paths.py:46`.

- **Option 3: per-task-attempt dispatch instrumentation** (a
  different v3.12.1 #5 already exists) — not directly relevant here.

- **Disable race-diag instrumentation** (commit `289db74`)
  Not disabled. Still useful for any future investigation, and the
  diff is small (5 lines + comments).

## 6. Future work (v3.12.5 / v3.13.0)

When ready to resume:

1. Grep `asyncio.create_task` / FastAPI `BackgroundTasks` / `add_task`
   across `src/` to find any background hermes invocations we missed
   (server may spawn hermes from a request handler's background task
   rather than the supervisor tick).
2. Confirm wrapper `_run_task` has only one caller (`_process_one`
   in `agent_cli.py:3854-3861`). Grep for `_run_task(` everywhere.
3. Add a hermes-side trace: `print(traceback.format_stack())` from
   inside `hermes_cli/profiles.py:1817` and `:2222` to identify which
   Python process is calling `set_active_profile` / `resolve_profile_env`
   when the fail happens. This bypasses our `src/`-only grep blind spot.
4. Once spawn location is confirmed, pick the right fix:
   - Server-side → per-profile hermes serialization (asyncio.Lock
     keyed by `(agent_id, profile_name)`)
   - Wrapper-side → add `subprocess.Popen` retry on the
     "Profile does not exist" stderr pattern
   - state.db contention → hermes-side retry with backoff

5. **Always include a "the EXACT repro" test case in the regression
   set** (per the v3.12.3 pattern). Concretely: capture the
   `hermes.t-<tid>.stderr.log` content from a fail task, plus the
   full dispatch payload, and add an integration test that asserts
   the new code path correctly produces it.

## 7. Related notes

- **Wrapper lifecycle (independent, high priority):** Task Scheduler
  has only `MSFT_TaskBootTrigger` and no recurring trigger. If the
  wrapper dies between reboots (or via clean self-restart), Task
  Scheduler does NOT auto-respawn. Wrapper self-restart exits with
  code 0 (clean), which doesn't trigger `RestartOnFailure`. Tracked
  separately as v3.12.5 #1-#3 — see wrapper-lifecycle fix commit.
- **Factory reset:** two resets were performed on 2026-08-04
  (`_backups/hermes-orch.pre-reset.20260804-181601.db` 116MB,
  `_backups/hermes-orch.pre-reset.20260804-210054.db` 5.8MB) to
  give the test batches a clean state.
