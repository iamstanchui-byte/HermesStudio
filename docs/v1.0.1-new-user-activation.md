# v1.0.1 — New User Activation Milestone

> **Status**: Draft (v1.0.1 — incorporates review notes, ready for sign-off)
> **Related**: `docs/install-spec.md` (overall productize spec) — this doc carves out the activation subset.
> **Target**: A new user can install server → safely connect one agent host → run one starter → see one completed task — **without opening repo documentation**.

## v1.0.1 Changelog (vs v1.0)

| # | Change | Why |
|---|---|---|

## 1. Background

Today a new user who follows the README and the `install-spec.md` to first run:

- Server boots with `host: 0.0.0.0` (regression — spec said 127.0.0.1) → dashboard exposed on LAN by default
- `/login` → `/setup-password` → lands on empty `/agents` (no agents, no projects, no workflows)
- LLM provider is on `/settings#llm`, agent host install instructions are on `docs/install-spec.md §8` (not in dashboard)
- No "starter" workflow exists; user must build one from scratch
- Server doesn't display its LAN IP (agent host install needs the IP, not `localhost`)
- No way to verify the system works end-to-end

**Goal**: a "new-user activation v1" milestone that takes the user from `pip install` → first completed task with **zero docs-read required**.

## 3. Architecture

### 3.1 Network model

| Layer | Default | User can enable |
|---|---|---|
| Dashboard bind | `127.0.0.1:8765` (loopback only) | `0.0.0.0:8765` (LAN + loopback) |
| HMAC agent auth | required (already in v1.6+) | unchanged |
| Dashboard cookie auth | required (already in v3.4) | unchanged |
| CORS / open CORS for agent host | off | post-v1.0 |

**Toggle = config + restart.** A live socket listener cannot rebind without a restart. Spec:

```text
User enables "Allow LAN access" in /settings#network
  → server persists desired_bind_host = "0.0.0.0"
  → server writes restart-required flag (~/.hermes-orchestrator/restart-required.flag)
  → server logs: "Restart required to apply network-access changes"
  → user clicks "Restart server" OR installer / systemd watchdog restarts it
  → server reads desired_bind_host, binds to 0.0.0.0
  → /settings#network UI updates to show active bind + LAN IP + enrollment command
```

**Disable LAN access** has the same restart semantics. No silent failure mode where the UI says "enabled" but the socket is still loopback.

#### 3.1.1 Config key migration (`host` → `bind_host`) — **v1.0.1 new**

v1.0 renamed the config key from `host` to `bind_host`. Existing installs have a config file with
`host: 0.0.0.0` (or `host: 127.0.0.1`) and no `bind_host` key at all. To avoid silently discarding
an explicit prior choice:

```text
Config loader resolution order:
  1. If `bind_host` key is present → use it.
  2. Else if legacy `host` key is present → use it, and log once at startup:
     "Migrating legacy config key 'host' -> 'bind_host' (value: <value> retained)."
  3. Else → default to "127.0.0.1".

On the next explicit config save (via /settings#network "Apply changes" or `init`),
the config file is rewritten with `bind_host` and the legacy `host` key is removed.
```

This guarantees an operator who previously opted into `host: 0.0.0.0` does not get silently
downgraded to loopback-only on upgrade, while still allowing T0.1 (fresh installs default to
`127.0.0.1`) to hold.

### 3.1.2 `POST /api/server/restart` process modes — **v1.0.1 new**

v1.0 left restart behavior ambiguous between "operator restarts manually" and "logged but not
auto-applied." This is now fully specified:

```text
POST /api/server/restart (admin-only, requires restart-required flag to be set):

1. Supervised mode (detected via HERMES_SUPERVISED=systemd|nssm env var, set by the
   watchdog/install script):
     - Server calls sys.exit(0).
     - The external supervisor (systemd / NSSM) restarts the process automatically.
     - Response: 202 Accepted, body {"mode": "supervised", "message": "Restarting via supervisor..."}

2. Direct / dev mode (no supervisor env var detected, but process was started as a
   normal foreground/background process):
     - Server performs an in-place re-exec: os.execv(sys.executable, [sys.executable] + sys.argv)
     - This preserves the same PID's parent shell session where possible.
     - Response is sent BEFORE the execv call: 202 Accepted,
       body {"mode": "self-exec", "message": "Restarting in place..."}

3. Undetectable mode (cannot determine how the process was started, e.g. embedded/
   frozen executable without a reliable argv):
     - No restart is attempted.
     - Response: 501 Not Implemented,
       body {"mode": "manual", "message": "Please restart the server manually
       (Ctrl+C and re-run `hermes-orch serve`)."}
     - UI displays this message verbatim with a "Copy restart command" button.
```

The `/settings#network` UI must reflect which mode was used/attempted so the user isn't left
guessing whether the click did anything.

### 3.2 User onboarding state

```sql
ALTER TABLE users ADD COLUMN onboarding_state TEXT NOT NULL DEFAULT '{}';
-- JSON shape:
-- {
--   "password_set": bool,
--   "llm_configured": bool,
--   "agent_connected": bool,
--   "first_task_completed": bool,
--   "first_task_attempted": bool
-- }
```

State transitions (who flips what, when):

| Field | Set `true` by | When |
|---|---|---|
| `password_set` | `POST /api/auth/setup` | first successful password set |
| `llm_configured` | `POST /api/settings/llm` (real key) OR explicit "Use Mock mode" button | real key saved OR user explicitly opts into mock |
| `agent_connected` | `POST /api/agents/{id}/heartbeat` | first heartbeat from any agent on the user's workspace |
| `first_task_completed` | `POST /api/tasks/{id}/result` | task with `status='completed'` |
| `first_task_attempted` | `POST /api/tasks/{id}/result` | any terminal status (completed OR failed) |

**Checklist collapse rule**: only when `password_set AND llm_configured AND agent_connected AND first_task_completed` are all true. `first_task_attempted` is informational only.

**Skip mechanism (single, canonical)**: each step in the checklist has one "Skip for now" link
(§3.6). There is no separate "skip all" affordance — this avoids two competing skip semantics.
Skipped steps remain visible on next visit.

**Reset rule**: user can re-open the checklist via `/settings#onboarding` → "Reset onboarding state" (admin-only, for re-demo).

#### 3.2.1 Backfill for existing users on upgrade — **v1.0.1 new**

v1.0 defaulted every existing user's `onboarding_state` to `{}` (all false) after the migration
runs, which would make an already-active user see the new-user checklist again — a UX regression.
Instead:

```sql
-- One-time backfill, run once as part of the migration that adds the column,
-- BEFORE the column's default is relied upon by application code:

UPDATE users SET onboarding_state = json_object(
  'password_set', 1,  -- if the user row exists and has a password_hash, they've set one
  'llm_configured', (
    CASE WHEN EXISTS (SELECT 1 FROM settings WHERE key = 'llm_provider')
         OR EXISTS (SELECT 1 FROM settings WHERE key = 'mock_mode' AND value = 'true')
    THEN 1 ELSE 0 END
  ),
  'agent_connected', (
    CASE WHEN EXISTS (SELECT 1 FROM agents WHERE last_heartbeat_at IS NOT NULL)
    THEN 1 ELSE 0 END
  ),
  'first_task_completed', (
    CASE WHEN EXISTS (SELECT 1 FROM tasks WHERE status = 'completed')
    THEN 1 ELSE 0 END
  ),
  'first_task_attempted', (
    CASE WHEN EXISTS (SELECT 1 FROM tasks WHERE status IN ('completed', 'failed'))
    THEN 1 ELSE 0 END
  )
);
```

Effect: an existing, already-active installation will have all four success signals backfilled to
true (in the common case) and the checklist collapses immediately on first login post-upgrade,
with no behavior change visible to the user. A genuinely fresh install (no agents, no tasks) still
correctly backfills to all-false and shows the checklist, matching new-user behavior.

### 3.3 Enrollment token

Chicken-and-egg solved by **workspace-scoped, agent-name-agnostic tokens**.

```sql
CREATE TABLE IF NOT EXISTS enrollment_tokens (
    id              TEXT PRIMARY KEY,
    token_hash      TEXT NOT NULL UNIQUE,    -- SHA-256 of plaintext token; never store plaintext
    created_by      TEXT NOT NULL,           -- user_id who issued it
    created_at      TEXT NOT NULL,
    expires_at      TEXT NOT NULL,           -- created_at + 15 min default
    used_at         TEXT,                    -- null until consumed
    used_by_agent_id TEXT,                   -- FK to agents.id (set on consume)
    requested_agent_name TEXT,                -- optional hint from operator; agent self-declares name on enroll
    label           TEXT                      -- e.g. "Home laptop", shown in UI only
);
CREATE INDEX idx_enrollment_tokens_hash ON enrollment_tokens(token_hash);
CREATE INDEX idx_enrollment_tokens_expires ON enrollment_tokens(expires_at);
```

**Issue flow** (dashboard → user):

```text
POST /api/enrollment-tokens  { label?: "Home laptop", requested_agent_name?: "win-01" }
  → server generates 256-bit random token (secrets.token_urlsafe(32))
  → server stores token_hash = SHA-256(token)
  → response: { id, token: "plaintext-shown-once", expires_at, install_command: "<copyable>" }
  → UI shows: "Token shown once. Expires in 15 min."
  → install_command is the one-liner the user pastes on the agent host
```

**Consume flow** (agent host → server):

```text
Agent runs: hermes-orch-agent enroll --server URL --token TOKEN --agent-name "win-01"
  → wrapper POST /api/enrollment-tokens/consume
     body: { token: "plaintext", agent_name: "win-01", hostname: "..." }
  → server (ATOMIC transaction):
     1. SELECT token_hash row by SHA-256(token); if missing → 404
     2. If expires_at < now → 410 expired
     3. If used_at IS NOT NULL → 410 already used
     4. UPDATE token SET used_at = now
     5. INSERT agent row (or MATCH by requested_agent_name; the agent-declared
        `agent_name` from the request body ALWAYS wins over `requested_agent_name` —
        see §3.3.2)
     6. UPDATE enrollment_tokens SET used_by_agent_id = <new agent.id>
        WHERE id = <token.id>  (same transaction — v1.0.1 fix)
     7. INSERT per-agent hmac_secret (separate from token)
  → response: { agent_id, hmac_secret: "long-lived-shown-once" }
  → wrapper stores hmac_secret in agent.yaml (mode 0600)
  → wrapper starts heartbeating with HMAC (existing v1.6 path)
```

**Atomicity**: the SELECT-then-UPDATE pattern with `WHERE expires_at > now AND used_at IS NULL` in a single UPDATE statement ensures two concurrent consumes resolve cleanly. SQLite single-writer serializes this for us; the busy_timeout=5000 PRAGMA (already shipped in v3.12.2) makes the read path wait.

**Plaintext token is never stored** — only the SHA-256 hash. If the DB leaks, tokens cannot be replayed.

#### 3.3.1 Known limitation: token visible via `ps aux` during install — **v1.0.1 new**

The `install_command` passes the plaintext token as a CLI argument (`--token etok-...`). During
the brief execution window, any other local process/user on the same agent host could observe the
token via `ps aux` or equivalent. Given the token's 15-minute expiry and single-use consumption,
this is an **accepted risk for v1.0.1**: the exposure window is short and the blast radius is
limited to obtaining a one-time enrollment (not a standing credential). This is surfaced to the
user via a UI tooltip on the install command:

> "This command contains a temporary token valid for 15 minutes. Avoid running it on a
> multi-user or shared host if that's a concern."

Deferred to v1.1: stdin-based or short-lived-URL-based token delivery that avoids putting the
token in argv.

#### 3.3.2 Precedence: agent-declared name vs requested hint — **v1.0.1 new**

`requested_agent_name` (set at token issue time) is a **UI pre-fill convenience only** — it has no
enforcement effect. The `agent_name` declared by the agent itself in the consume request body
**always wins**. If they differ (e.g. dashboard issued a token hinting "win-01" but the agent host
runs `enroll --agent-name win-02`), the agent record is created/named `win-02` with no error and
no silent coercion. The UI may show a one-time informational note: "Agent enrolled as 'win-02'
(requested name 'win-01' was not used)."

### 3.4 Starter catalog (bundled, read-only)

```
src/hermes_orch/starters/
├── research-brief.yaml
├── system-health.yaml
├── backtest-stater.yaml
└── daily-monitor.yaml
```

Each YAML has the same shape as a `workflow_packages` row's `step_template` + `variables`, plus a `display` block:

```yaml
name: research-brief
display:
  title: "Research brief"
  description: "2-3 paragraph summary of any topic with sources"
  icon: "📚"
  category: "research"
  mock_mode_supported: true
  estimated_minutes: 5
step_template:
  - name: search-sources
    agent_role: super
    action: web_search
    depends_on: []
    params_template:
      query: "{{topic}}"
      max_results: 10
  - name: write-summary
    agent_role: super
    action: compose_text
    depends_on: [search-sources]
    params_template:
      style: "executive_brief"
      sources: "{{search-sources.output}}"
variables:
  - name: topic
    type: string
    required: true
    description: "Topic to research"
required_capability: web_search
```

**Loaded at server startup** (in-process, no DB writes for the catalog). `GET /api/starters` returns the list. `POST /api/starters/{name}/clone` creates a `workflow_packages` row (user-owned, source untouched). Versioning: catalog YAML has a `version` field; user clones get a snapshot — updates to the catalog don't auto-migrate user clones. User can "Update to latest" via a button on the workflow detail page (separate endpoint, post-v1.0).

### 3.5 Mock-mode system health smoke test

The `system-health` starter is a **special-case workflow** that the server handles without dispatching to an agent. It runs entirely in-process to verify the server→agent→result pipeline is healthy.

```yaml
name: system-health
display:
  title: "System health check"
  description: "Verify server can reach your agent host end-to-end (no LLM needed)"
  icon: "🩺"
  category: "diagnostics"
  mock_mode_supported: true
  estimated_minutes: 1
step_template:
  - name: ping-agent
    agent_role: super
    action: _server_healthcheck  # special action handled in-process
    depends_on: []
    params_template: {}
variables: []
```

**Server-side handling**: when the supervisor sees `action = "_server_healthcheck"`, it skips agent dispatch and synthesizes a result:

```json
{
  "status": "completed",
  "summary": "Server ↔ agent connection OK. Last heartbeat: 4s ago.",
  "details": {
    "agent_id": "...",
    "agent_hostname": "...",
    "last_heartbeat_at": "...",
    "registered_profiles": ["super", "super-b"],
    "queued_tasks": 0
  }
}
```

**Why a server-side special action and not a real LLM call**: the smoke test must succeed in mock mode (no API key) and on a fresh install (no real tasks run yet). The result is the proof that the **plumbing works**, not that the LLM is smart.

#### 3.5.1 Zero-agent and multi-agent behavior — **v1.0.1 new**

v1.0 assumed there was exactly one agent to ping. This is now defined for all cases:

```text
Zero registered agents on the workspace:
  → status = "failed"
  → summary = "No agent connected yet — connect one first."
  → details = { "registered_agents": 0 }
  → This flips `first_task_attempted`, NOT `first_task_completed`
    (a health check against zero agents cannot be a "successful" first task).

One registered agent:
  → behavior as originally specified (ping that agent, report its heartbeat).

Two or more registered agents:
  → ping ALL registered agents on the workspace.
  → status = "completed" if at least one agent has a heartbeat within the
    last 60 seconds; "failed" otherwise.
  → summary lists each agent individually, e.g.:
    "2/2 agents reachable. win-01: last heartbeat 3s ago. linux-a01: last
    heartbeat 41s ago."
  → details.registered_agents = [{agent_id, hostname, last_heartbeat_at}, ...]
```

### 3.6 The 4-step first-run checklist

**Always shown at `/` when onboarding incomplete**:

```text
Welcome to Hermes Nexus

✓ 1. Set your password                   (done — you logged in)
□ 2. Choose how to run LLMs
     [Use Mock mode]  [Configure provider]
     Mock mode lets you try the system without an API key.
□ 3. Connect an agent host
     [Show install command]
     Status: No agent connected
□ 4. Run a starter workflow
     [Research brief] [System health check] [Backtest starter]
     Once a task completes, this section collapses.
```

**Skippable**: each step has a "Skip for now" link (the single, canonical skip mechanism — see
§3.2). **Recoverable**: a `?` icon next to each step shows a short tooltip + link to full docs.

**Collapse**: when all 4 success signals are true → redirect to `/agents` and never re-show the checklist unless `/settings#onboarding` → "Reset onboarding state" is hit (admin-only).

### 3.7 Known limitation: restart does not drain in-flight tasks — **v1.0.1 new**

Triggering a server restart (§3.1.2) does not gracefully wait for in-flight tasks to finish. Any
task in `running` status at the moment of restart will be interrupted; its status may remain
`running` in the database until the agent's next heartbeat/reconciliation cycle corrects it. This
is an accepted v1.0.1 limitation, not an oversight:

- Restarting is only needed for network-bind changes (§3.1), an infrequent, deliberate admin
  action — not part of normal operation.
- Graceful drain (wait for in-flight tasks, refuse new dispatch, then restart) is deferred to v1.1,
  tracked alongside the workflow-level graceful-cancel work in the human-approval spec.

The `/settings#network` UI shows a warning before restart if any tasks are currently `running`:

> "N task(s) are currently running. Restarting now will interrupt them. Continue?"

| `GET` | `/api/settings/bind-host` | `{ "active": "127.0.0.1", "desired": "0.0.0.0", "lan_enabled": false }` |

| `POST` | `/api/server/restart` | Trigger restart (admin-only, requires restart-required flag). See §3.1.2 for the 3 process-mode behaviors and response shapes. |

The active bind is read-only (only changes on actual restart). The desired bind is what the UI toggle writes to.

### 5.5 First-run checklist UI

| Method | Path | Purpose |
|---|---|---|
| `GET` | `/` | Returns `templates/onboarding.html` if `onboarding_state` incomplete; else redirects to `/agents` |

No API call — the user is already authenticated (cookie present). State is read from the cookie's user row.

## 8. Migration / rollout

1. **Additive only** — no destructive migrations
2. **Backwards-compat for network config** — `host` key is read via fallback (§3.1.1); users on existing `host: "0.0.0.0"` config keep that behavior on upgrade, it is not silently downgraded. `init --bind-host 0.0.0.0` flag for users who explicitly want LAN on for a fresh install.
3. **No DB schema migration for users who don't want LAN** — the bind is config-file only
4. **`onboarding_state` backfill, not blanket reset** — existing users get their state computed from real system data (§3.2.1); only genuinely fresh installs see all-false and the checklist. There is exactly one skip mechanism ("Skip for now" per step); no separate "skip all."
