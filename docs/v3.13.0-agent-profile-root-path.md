## 1. Background

Goal：半技術 user 應該可以純靠 dashboard 管理多台 agent + 多個 profile，**唔需要 SSH 落 host 改 JSON / env**。

現狀：

- Dashboard「+ Add profile」form（templates/agents.html:298-315）只有：
  - `name`（e.g. "win-agent02"）
  - `description`（optional）
- POST `/api/agents/{id}/profiles`（api/agents.py:1046-1105）只寫入：
  - `id, agent_id, name, description, status, capabilities, storage_refs, skills`
  - **無任何 path / root field**
- Agent host wrapper 啟動時會 auto-sync role list：

  ```python
  existing_cfg = load wrapper-config.json
  new_roles = GET /api/agents/{id}/profiles

  for role in new_roles:
      if role not in existing_cfg:
          candidate = detect_hermes_profiles_dir() / role
          if candidate.exists():
              merged[role] = {"root": "<profiles_dir>/<role>"}
  ```

  （agent_cli.py:1732-1752 — `start` 內嵌 auto-sync；亦係 agent_cli.py:4036+ 嘅 `sync-config` standalone command 嘅核心邏輯）

- Path resolution priority（agent_paths.py:resolve_profile_root）：

  1. `wrapper-config.json["root"]`（explicit）
  2. `"<profiles_dir>/<role>"`（auto template）
  3. `HERMES_PROFILES_DIR` env + `/<role>`
  4. OS default（`%LOCALAPPDATA%/hermes/profiles/<role>`、`~/.local/share/hermes/profiles/<role>`）
  5. 相對 `./<role>`（last resort）

Wrapper 目前**已經尊重 explicit `"root"`**（Step 1），但 orchestrator 端冇方法透過 UI 幫 user 設定呢個 field。

## 2. Problem

實際遇到嘅 failure modes：

1. **Custom install 路徑**（e.g. `D:\tools\hermes\` 而唔係 `%LOCALAPPDATA%`）
   - auto-derive 走去 default base dir，wrapper 報 `FileNotFoundError`
2. **NAS / SMB mount**（e.g. `\\nas\share\hermes\profiles\<role>`）
   - auto-derive 唔識 network share 路徑，profile 啟動失敗
3. **Per-profile custom path**（A local, B NFS）
   - 現有策略係「一個 base dir，所有 profile 一齊塞入去」，不能 per-role root
4. **不同 hermes version per profile**
   - 系統 assume `1 host = 1 hermes install`，但複雜部署中經常 `1 host = N hermes dir`（A/B / canary）

現有 escape hatch 全部要 SSH：

- 設 `HERMES_PROFILES_DIR` env（甚至要入 Task Scheduler service 環境）
- 直接 edit `wrapper-config.json` 寫 `"root": "/custom/path"`
- 設 `HERMES_BIN` env（binary path）

對半技術 user，呢啲操作摩擦極高，亦同 orchestrator「用 dashboard 管 agent」嘅 product 目標相違背。

## 3. Goals / Non-goals

Goals：

- 允許 user 在 **dashboard 建 profile 時直接填寫「root path on host」**。
- 由 orchestrator 把呢個 root path 傳俾 agent host wrapper，同步入 `wrapper-config.json["root"]`。
- 保持現有 auto-derive 行為作 default；未填 root 的 profile 無需更改。

Non-goals：

- orchestrator **唔會 SSH / WinRM 落 host**，唔做 remote filesystem 改動。
- orchestrator **唔驗證 path 真的存在**；host-side discovery / existence check 仍然係 wrapper 嘅責任。
- 唔重寫 `resolve_profile_root` algorithm，保留所有現有 fallback 階層。
- 唔處理「每 profile 用唔同 Hermes binary」的全套版本管理；只提供 profiles root path 配置。
- 唔在 v3.13.0 範圍內加 wrapper 即時 in-process reload（詳見 Section 4.6）。
- **v3.13.0 不再支援 SQLite < 3.35 作 production DB**。`ALTER TABLE ... ADD COLUMN IF NOT EXISTS` 需要 SQLite 3.35+。Orchestrator 啟動時 check `sqlite_version()`, 如 < 3.35 而且 `agent_profiles.root_path` column 已經存在（即需要但尚未 migrate）就 warning + exit 1。對運維 team 而言，舊 SQLite 升級係 migration 先決條件。

## 4. Proposed solution (Option 1)

### 4.1 Dashboard UI change

在「+ Add profile」form 加一個 optional field：

- Label：`Root path on host`（tooltip: "The absolute path to this profile's directory on the agent host, e.g. D:\tools\hermes\profiles\win-agent02 or /mnt/nas/hermes/profiles/quant-prod."）
- Field 名：`root_path`（string, optional）

編輯現有 profile 時亦顯示同一欄位：

- Edit profile modal 顯示 `root_path` 以便修改。
- 留空時維持 auto-derive 行為。

Validation（前端）：

- 只做 basic validation：
  - 非空時必須為非空字串。
  - 不做 OS-specific slash / backslash 強制轉換，由 host wrapper 負責解讀。
- 不試圖驗證 path 存在或可寫。

UX 提示：

- 如果 user 填寫 `root_path`，底部提示一行：
  - "The wrapper will use this path as the profile root. Make sure this directory exists on the agent host; Hermes Orchestrator does not create or validate it."
- 如果 user 留空，顯示輕提示：
  - "If left empty, the agent wrapper will auto-detect the profile location based on the host's Hermes installation."

### 4.2 DB schema change

在 `agent_profiles` table 加一個 nullable column：

- Column 名：`root_path`
- 型別：`TEXT NULL`
- Migration（**idempotent**）：
  ```sql
  -- SQLite 3.35+ supports IF NOT EXISTS on ALTER TABLE ADD COLUMN.
  -- Older SQLite will fail; orchestrator should refuse to start if
  -- sqlite_version < 3.35 and the column is already added.
  ALTER TABLE agent_profiles ADD COLUMN IF NOT EXISTS root_path TEXT NULL;
  ```
- 兼容舊 data：所有現有 profile `root_path = NULL`，維持 auto-derive 行為。
- Orchestrator 啟動時嘅 migration runner 應 skip-and-warn 而唔係 crash（已存在嘅 column 唔再 attempt add）。

### 4.3 API change

#### 4.3.1 `POST /api/agents/{id}/profiles`

Request body 增加：

```json
{
  "name": "win-agent02",
  "description": "Windows agent for quant backtests",
  "root_path": "D:\\tools\\hermes\\profiles\\win-agent02"
}
```

行為：

- 若 `root_path` 缺省或為空字串 / `null`，寫入 DB 作 `NULL`，UI / wrapper 視為「無 explicit root」。
- 若 `root_path` 非空，寫入 DB，後續 sync-config 使用。

#### 4.3.2 `PATCH /api/agents/{id}/profiles/{profile_id}`

支援更新 `root_path`：

```json
{
  "root_path": "\\\\nas\\share\\hermes\\profiles\\quant-prod"
}
```

行為：

- 隻改 `root_path`，其他欄位不變（除非 request body 包含）。
- 將 `root_path` 設為 `null` 等同 clear explicit root，回退 auto-derive。

後端 validation：

- 若提供 `root_path`，必須為非空字串；不做 path existence check。
- `root_path` 可包含 OS-specific path syntax（`C:\...`、`\\nas\...`、`/...`），後端不嘗試 normalize。

### 4.4 Wrapper sync-config change（agent host）— **兩處都要改**

⚠️ **v2 重要**: `root_path` merge 邏輯出現喺 wrapper 兩處，**必須兩處都更新**，否則出現以下 bug：
- 只改 `sync-config`：wrapper 首次 `start` 唔會用 root_path（要 manual `sync-config` 先得）
- 只改 `start` block：operator `sync-config` 嗰陣唔會用 root_path

**兩處位置**：
- `agent_cli.py:1732-1752` — `start` command 內嵌嘅 auto-sync block
- `agent_cli.py:4036-4125` — `sync-config` standalone command

**建議抽出 shared helper**（推薦做法）：

```python
# 新 helper，喺 agent_cli.py 頂部
def _merge_orch_profiles_into_config(
    cfg: dict,
    orch_profiles: list[dict],
    detected_profiles_dir: Path | None,
) -> tuple[dict, list[str]]:
    """Merge orchestrator-reported profile list into wrapper-config.

    v3.13.0 conservative behavior (per AC-6):
      - All EXISTING cfg entries are treated as user-managed
        ("manual override") and are NEVER overwritten by the
        orchestrator — even when the orch reports a `root_path`.
      - For NEW roles (not in existing cfg):
          - if `root_path` is set: use it as `"root"`
          - else: try auto-derive from <detected_profiles_dir>/<role>
          - else: fall back to relative `./<role>`

    Future (v3.14.0+): differentiate "auto-derived" vs "manually
    overridden" entries via a `source: "auto" | "manual"` metadata
    field in wrapper-config.json, then orchestrator's `root_path`
    can override auto-derived entries. See AC-7 (stretch goal).

    Returns (merged_cfg, list_of_added_role_names).
    """
    existing = cfg.get("profiles") or {}
    merged = dict(existing)
    added = []
    for p in orch_profiles:
        role = p["name"]
        root_path = (p.get("root_path") or "").strip()
        if role in existing:
            # v3.13.0: conservative — preserve whatever's in the
            # wrapper-config.json. This is correct for manual edits
            # AND for entries the previous run of this helper wrote
            # (auto-derive). The helper is idempotent on re-runs.
            # Stretch goal (v3.14.0): see docstring above.
            continue
        if root_path:
            merged[role] = {"root": root_path}
            added.append(role)
            continue
        if detected_profiles_dir:
            candidate = detected_profiles_dir / role
            if candidate.exists():
                merged[role] = {"root": str(candidate)}
                added.append(role)
                continue
        # Last resort: relative path; wrapper will fail later if invalid
        merged[role] = {"root": f"./{role}"}
        added.append(role)
    return merged, added
```

兩處 sync block 都 call 呢個 helper。`start` block 同 `sync-config` 都改用同一個 function。

行為要點：

- **v3.13.0 conservative 行為**: 所有已有 cfg entry 一律視為 manual override，**唔會**被 orchestrator `root_path` 覆蓋（即使 orch 報咗 root_path, 只要 cfg 已經有 entry, 就 skip）。
  - 對應 AC-6
  - 對應 helper 入面 `if role in existing: continue` 嗰行
  - **Idempotency 保證**: 因此 v3.13.0 中 `_merge_orch_profiles_into_config` 對已有 entry 是完全 idempotent, **唔會改寫任何現有 wrapper-config.json** (即使再 call 100 次, 結果一樣)。Operator 可以放心喺 host 行 `hermes-orch-agent sync-config` 任意次數。
- 對**新加**嘅 role（cfg 入面冇 entry）: `root_path` 存在就用，否則 auto-derive，否則 `./<role>` fallback。
- **`root_path` 指向不存在嘅目錄**: wrapper 啟動後會以現有邏輯報錯（e.g. `FileNotFoundError`），orchestrator 不阻止。
  - **唔會** auto-fallback 到 `<profiles_dir>/<role>` — 一旦 user 明確填寫 root_path, 就視為 authoritative 設定，silent fallback 會令 debug 困難。
  - 對應 AC-8
- **未來改進 (v3.14.0+, AC-7 stretch goal)**: 加 `source: "auto" | "manual"` metadata 入 `wrapper-config.json`, 然後 helper 可以分辨「auto-derive entry」vs「manual entry」, orchestrator `root_path` 只覆蓋 auto 嗰啲。v3.13.0 唔做。

### 4.5 Path resolution priority 保持不變

`resolve_profile_root` 順序保持：

1. `wrapper-config.json["root"]`（explicit）
2. `"<profiles_dir>/<role>"`（auto template）
3. `HERMES_PROFILES_DIR` env + `/<role>`
4. OS default（`%LOCALAPPDATA%/hermes/profiles/<role>` / `~/.local/share/hermes/profiles/<role>`）
5. `./<role>`（last resort）

新加的 `root_path` 只是透過 orchestrator 幫 user **寫入第 1 步「explicit root」**，而唔改後面 fallback。

### 4.6 Wrapper restart limitation（**v2 新增**）

⚠️ **Known limitation**: 改 `root_path` from dashboard 唔會 trigger in-process wrapper reload。流程：

1. User 喺 dashboard 改 `root_path` → DB row updated
2. 現有 running wrapper 仲係用舊嘅 `wrapper-config.json`（in-memory cache）
3. 下一個 TimeTrigger restart（最長 5 min）→ wrapper `start` block call helper → pick up 新 root_path
4. 或者 operator 喺 host 行 `hermes-orch-agent sync-config && restart`

Workaround for v3.13.0：
- Document 呢個 limitation 喑 user 知要等最多 5 分鐘
- 「Last synced: 2 min ago」之類嘅 indicator 喑 user 知 wrapper config 嘅 freshness

長期方案（v3.14.0+，out of scope for v3.13.0）：
- Option A: Orchestrator push SSE/webhook → wrapper in-process reload
- Option B: Wrapper self-polling `/api/agents/{id}` 每 30s, 見到 config change 就 reload
- Option C: Wrapper expose `/api/wrapper/reload-config` endpoint, 觸發 in-process reload

## 5. UX / error handling

### 5.1 Dashboard 提示

在 Add/Edit profile modal 中：

- 若 `root_path` 留空：顯示輕提示 "If left empty, the agent wrapper will auto-detect the profile location based on the host's Hermes installation."
- 若 `root_path` 填寫：顯示警示 "Make sure this directory exists on the agent host. Hermes Orchestrator does not create or validate it."

### 5.2 Wrapper error surface

Wrapper 若因 profile root path 不存在而失敗：

- 保持現有 log / error 行為，不由 orchestrator 介入
- Profile status 保持 `idle`（不 claim tasks）
- 日後可考慮在 orchestrator agent detail 頁面顯示「profile root not found」訊息（out of scope for v3.13.0）

### 5.3 Backwards compatibility

- 舊 data: 所有現有 profile `root_path = NULL` → helper 走 `root_path` 為空嘅 branch，行為 100% 同改之前一樣
- 舊 `wrapper-config.json`: 已 explicit 寫咗 `"root"` 嘅 entry → helper 唔覆蓋（respect manual override）
- 舊 client code (dashboard form 無 root field): 個 field 留空 = NULL，唔影響舊 user

### 6.1 Release train rationale（**v3 新增**）

本 change 不影響 v3.12.x 已完成嘅 wrapper lifecycle（v3.12.4 race investigation + v3.12.5 self-restart fix + v3.12.6/7/8 incremental editing + token usage）任何工作。因此排期喺 v3.13.0，以免擾亂現有 release train。Migration 喺 fresh install + upgrade path 兩條路徑都安全：column nullable, 預設 `NULL`, 既有 code path 唔需要 detect `root_path` column 存在與否。

## 7. Future work (out of scope for v3.13.0)

唔喺本 spec 入面，但可以作為後續方向：

- **Wrapper 即時 in-process reload** (Section 4.6 提及): SSE push / polling / dedicated endpoint
- **Host-side manifest** (e.g. `agent-manifest.json`): import host 上既有 profile layout
- **Wrapper self-discovery + report**: 適合「從 host import」模式
- **Path existence check + UI surfacing**: orchestrator agent detail 頁面顯示「指定 root path 不存在」紅色 banner
- **更進階的 per-profile Hermes binary / version management**: 一 host 多 hermes version（每 profile 用唔同 binary）
- **Cross-host profile migration**: 將 profile 由 A host 搬去 B host, sync 埋 SOUL preset 同 storage_refs

## 8. Acceptance criteria (v2 新增)

Implementation 視為 complete 嘅條件：

| # | Scenario | Expected behavior |
|---|---|---|
| AC-1 | Dashboard `Add profile` 填 `root_path` → Save | DB row 有 `root_path` 非 NULL; wrapper config 下次 sync 帶呢個 value |
| AC-2 | Dashboard `Add profile` 留空 `root_path` → Save | DB row `root_path = NULL`; 行為同改之前一樣 (regression test) |
| AC-3 | Dashboard `Patch profile` 將 `root_path` 設為某 path | DB 更新; 下次 wrapper sync 使用新 path |
| AC-4 | Dashboard `Patch profile` 將 `root_path` 設為 `null` | DB `root_path = NULL`; wrapper 重新用 auto-derive |
| AC-5 | Wrapper `start`: orch 報 root_path + 已 existing cfg 無 entry | wrapper-config.json 嗰個 role 嘅 `"root"` = root_path (唔走 auto-derive) |
| AC-6 | Wrapper `start`: orch 報 root_path + 已 existing cfg 有 entry 但係手動 root | 保留手動 root (orch 唔覆蓋) — but: AC-7 講相反 case |
| AC-7 | Wrapper `start`: orch 報 root_path + 已 existing cfg 有 entry 係 auto-derive (e.g. `<profiles_dir>/<role>`) | v3.13.0 唔覆蓋 (保守). **(stretch goal, v3.14.0+)**: 加 `source: "auto"\|"manual"` metadata 後, 用 orch 嘅 root_path 覆蓋 auto-derive entry |
| AC-8 | Wrapper `start`: orch 報 `root_path` 但個 dir 唔存在 | Wrapper 報 `FileNotFoundError`; profile 保持 `idle`, 唔 claim tasks. **此錯誤唔會自動 fall back 到 auto-derive**; 一旦 user 明確填寫 root_path, 就視為 authoritative 設定 (避免 silent self-healing 難 debug) |
| AC-9 | 90% user case (standard install, 無 root_path) | 行為 100% 同 v3.12.8 一樣 (regression test pass) |
| AC-10 | 2 個 wrapper 共享同一個 host (one host = 1 agent 入面有 N profiles) | 互相唔干擾, 各 profile 各自用自己 root_path |

Sign-off 需要（v3.13.0）：

- **Hard requirements** (必須 pass): AC-1, AC-2, AC-3, AC-4, AC-5, AC-6, AC-8, AC-9, AC-10
- **Stretch goal** (唔阻 v3.13.0 簽署, 留待 v3.14.0+): AC-7

即 v3.13.0 簽署時 AC-7 **唔需要** pass，helper 邏輯亦唔覆蓋 auto-derive entry。文件化呢個 limitation 喑 user / future engineer 知，AC-7 嘅覆寫行為要等 wrapper-config schema 加 `source` metadata 先做到。
