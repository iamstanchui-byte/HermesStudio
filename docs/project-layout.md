## 2. Windows — server + client

Two separate things run on Windows. **Both** are required for the system to work.

### 2a. Orchestrator (server + dashboard)

**Source (dev repo)**: `C:\Project\minimax code\hermes-orchestrator\`

**Installed copy (used at runtime)**: same dir, just a venv. The venv is `C:\Project\minimax code\hermes-orchestrator\.venv\`. Both `hermes-orch` (server) and `hermes-orch-agent` (wrapper) are entry points from `pyproject.toml`'s `[project.scripts]`.

**Server exe (what you actually run)**:

```
C:\Project\minimax code\hermes-orchestrator\.venv\Scripts\hermes-orch.exe
```

Run with: `hermes-orch serve --reload` (port 8765).

**Server logs / runtime data** (separate from source — this is the operator's workspace):

```
C:\Users\stanley\.hermes-orchestrator\
├── admin-token.txt                  # 43-byte bearer token for the dashboard API
├── config.yaml                      # 901 bytes — runtime config
├── hermes-orch.db                   # 596 MB SQLite DB (the main state store)
├── wrapper-config.json              # 476 bytes — tells the wrapper where to find the server + its secret
├── .secret-<agent_id>               # per-agent HMAC secret (43 bytes)
├── memory/                          # 3-tier memory storage
├── projects/                        # project workspaces (plan.md, status.md, etc.)
├── artifacts/                       # agent output files
├── daemon.out.log, daemon.err.log   # the WRAPPER's logs (server is server.log/server.log.err in the source dir)
├── wrapper.out.log, wrapper.err.log # manual wrapper's logs (we use this since ditching NSSM)
├── wrapper.pid                      # PID of the wrapper process
├── scripts/                         # mirror of the source's scripts/
└── test-profiles/                   # hermes profiles for testing
```

Note the server's own logs (`server.log`, `server.log.err`) live in the source dir, not in `~/.hermes-orchestrator/`. The orchestrator's `pyproject.toml` is set up so `hermes-orch.exe` expects to be run from the source dir (so `CWD`-relative paths resolve correctly).

### 2b. Hermes CLI (the actual agent runtime)

The orchestrator **doesn't run the LLM directly**. It just schedules tasks. Each agent is a separate `hermes-cli` install. On Windows, the agent host is `win-local-1` (192.168.2.152).

**Hermes CLI install** (the third-party, not our code):

```
C:\Users\stanley\AppData\Local\hermes\hermes-agent\
├── venv/                            # Python 3.11 venv with hermes-cli installed
│   └── Scripts/
│       ├── hermes-cli.exe           # the actual CLI
│       ├── python.exe
│       └── ...
├── config.yaml
├── auth.json
└── ...
```

**Hermes profiles** (the per-role config the orchestrator dispatches to):

```
C:\Users\stanley\AppData\Local\hermes\profiles\
├── win-agent01\                     # role: win-agent01
│   ├── .env                         # hermes config (model, storage refs, etc.)
│   ├── .hermes_history
│   ├── .orch-cache\                 # per-project task outputs
│   ├── SOUL.md
│   └── skills\                      # SKILL.md files (flat + subfolder)
└── win-agent02\                     # role: win-agent02
    └── ...
```

**Wrapper install** (our code, runs on the agent host):

```
C:\Project\minimax code\hermes-orchestrator\.venv\Scripts\hermes-orch-agent.exe
```

The wrapper is launched with:

```
hermes-orch-agent start --config C:\Users\stanley\.hermes-orchestrator\wrapper-config.json --interval 5
```

It heartbeats every 5s to the orchestrator (port 8765), receives task assignments, runs them via the `hermes-cli` (subprocess), submits results back, syncs skills.

Control: `python scripts\wrapper-ctl.py {start|stop|restart|status}` (no admin needed since ditching NSSM).

## 3. Linux — client only

Linux is an **agent host only**, no orchestrator server. The orchestrator dispatches tasks to the Linux wrapper over the LAN.

**Linux host**: `linux-a-01` (192.168.2.161), user `stanley`. Two roles: `super` and `super-b`.

### 3a. Wrapper install (our code)

```
/home/stanley/.hermes-orchestrator/                    ← install root (pip install in a venv)
├── .secret-linux-a-01                                # HMAC secret for the orchestrator to authenticate this agent
├── wrapper-config.json                               # 351 bytes — orch URL + agent_id
├── memory/                                           # 3-tier memory mirror (synced from server)
└── venv/                                             # venv root
    ├── bin/
    │   ├── hermes-orch-agent                          # ← the wrapper exe shim (Python entry point)
    │   ├── hermes-orch                                # server entry (unused on this host — we only run the agent)
    │   ├── uvicorn, fastapi, httpx, dotenv, ...
    │   └── python -> python3
    └── lib/python3.12/site-packages/hermes_orch/      # ← THE ACTUAL CODE LIVES HERE (deployed via SCP)
        ├── __init__.py
        ├── __main__.py
        ├── main.py
        ├── cli.py
        ├── config.py
        ├── db.py
        ├── agent_cli.py                                # ← largest, 148 KB
        ├── agent_cli.py.bak.20260724_*                 # backups from each deploy-wrapper-linux.py run
        ├── agent_paths.py
        ├── agent_paths.py.bak.20260724_*
        ├── api/
        │   ├── __init__.py
        │   ├── agents.py
        │   ├── tasks.py
        │   ├── projects.py
        │   ├── workflows.py
        │   └── schedules.py
        └── core/
            ├── __init__.py
            └── synthesis.py
```

**The wrapper code is a pip install**, not a git checkout. To update, run `scripts/deploy-wrapper-linux.py` from the Windows dev box — it SCPs new `agent_cli.py` + `agent_paths.py`, backs up the old ones, kills the running wrapper, starts a new one with `setsid nohup`, waits for heartbeat, triggers skill sync.

**For permanent editable install** (changes to source on Windows are picked up on next wrapper restart):

```bash
ssh stanley@192.168.2.161
cd /home/stanley/.hermes-orchestrator
source venv/bin/activate
pip install -e /path/to/dev/src    # wherever the Windows dev source is mounted
```

## 5. Operations cheat sheet

### Daily dev (Windows)

```powershell
# After editing src/hermes_orch/api/* or core/* — reloads via WatchFiles automatically
# (but supervisor.py needs full restart, see memory entry #22)

# After editing src/hermes_orch/agent_cli.py:
python scripts\wrapper-ctl.py restart

# After editing template files (src/hermes_orch/templates/*):
# auto-reload, just refresh the browser

# Full server restart (when WatchFiles + supervisor get stuck):
python scripts\restart-server.py
```

### Linux updates

```powershell
# From Windows:
python scripts\deploy-wrapper-linux.py

# Then verify:
curl http://localhost:8765/api/agents  # should show linux-a-01 verified
```

### Inspect state

```powershell
# All agents
curl http://localhost:8765/api/agents

# Linux wrapper process
ssh stanley@192.168.2.161 'pgrep -fa hermes-orch-agent'

# Linux wrapper log
ssh stanley@192.168.2.161 'tail -30 /tmp/hermes-orch-agent.log'
```
